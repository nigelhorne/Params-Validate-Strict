  109: =head1	METHODS
  110: 
  111: =head2 validate_strict
  112: 
  113: Validates a set of parameters against a schema.
  114: 
  115: This function takes two mandatory arguments:
  116: 
  117: =over 4
  118: 
  119: =item * C<schema> || C<members>
  120: 
  121: A reference to a hash that defines the validation rules for each parameter.
  122: The keys of the hash are the parameter names, and the values are either a string representing the parameter type or a reference to a hash containing more detailed rules.
  123: 
  124: As an alternative the schema may be supplied as an B<arrayref of parameter hashrefs>,
  125: where every element describes one parameter and carries a mandatory
  126: C<name> key:
  127: 
  128:   $schema = [
  129:     { name => 'username', type => 'string', min => 3, max => 50 },
  130:     { name => 'age',      type => 'integer', min => 0, max => 150 },
  131:     { name => 'role',     type => 'string', optional => 1, default => 'user' },
  132:   ];
  133: 
  134: The arrayref form is normalised to the standard hashref form before any further
  135: processing.  It is particularly useful when declaration order matters (e.g.
  136: for positional or mixed calling conventions used by some CPAN modules).  The
  137: C<name> key is consumed during normalisation and does not appear as a
  138: validation rule.
  139: 
  140: For some sort of compatibility with L<Data::Processor>,
  141: it is possible to wrap the schema within a hash like this:
  142: 
  143:   $schema = {
  144:     description => 'Describe what this schema does',
  145:     error_msg => 'An error message',
  146:     schema => {
  147:       # ... schema goes here
  148:     }
  149:   }
  150: 
  151: =item * C<args> || C<input>
  152: 
  153: A reference to a hash containing the parameters to be validated.
  154: The keys of the hash are the parameter names, and the values are the parameter values.
  155: 
  156: =back
  157: 
  158: It takes optional arguments:
  159: 
  160: =over 4
  161: 
  162: =item * C<description>
  163: 
  164: What the schema does,
  165: used in error messages.
  166: 
  167: =item * C<error_msg>
  168: 
  169: Overrides the default message when something doesn't validate.
  170: 
  171: =item * C<unknown_parameter_handler>
  172: 
  173: This parameter describes what to do when a parameter is given that is not in the schema of valid parameters.
  174: It must be one of C<die>, C<warn>, or C<ignore>.
  175: 
  176: It defaults to C<die> unless C<carp_on_warn> is given, in which case it defaults to C<warn>.
  177: 
  178: =item * C<logger>
  179: 
  180: A logging object that understands messages such as C<error> and C<warn>.
  181: 
  182: =item * C<custom_types>
  183: 
  184: A reference to a hash that defines reusable custom types.
  185: Custom types allow you to define validation rules once and reuse them throughout your schema,
  186: making your validation logic more maintainable and readable.
  187: 
  188: Each custom type is defined as a hash reference containing the same validation rules available for regular parameters
  189: (C<type>, C<min>, C<max>, C<matches>, C<memberof>, C<values>, C<enum>, C<notmemberof>, C<callback>, etc.).
  190: 
  191:   my $custom_types = {
  192:     email => {
  193:       type => 'string',
  194:       matches => qr/^[^@\s]+\@[^@\s]+\.[^@\s]+$/,
  195:       error_msg => 'Invalid email address format'
  196:     }, phone => {
  197:       type => 'string',
  198:       matches => qr/^\+?[1-9]\d{1,14}$/,
  199:       min => 10,
  200:       max => 15
  201:     }, percentage => {
  202:       type => 'number',
  203:       min => 0,
  204:       max => 100
  205:     }, status => {
  206:       type => 'string',
  207:       memberof => ['draft', 'published', 'archived']
  208:     }
  209:   };
  210: 
  211:   my $schema = {
  212:     user_email => { type => 'email' },
  213:     contact_number => { type => 'phone', optional => 1 },
  214:     completion => { type => 'percentage' },
  215:     post_status => { type => 'status' }
  216:   };
  217: 
  218:   my $validated = validate_strict(
  219:     schema => $schema,
  220:     input => $input,
  221:     custom_types => $custom_types
  222:   );
  223: 
  224: Custom types can be extended or overridden in the schema by specifying additional constraints:
  225: 
  226:   my $schema = {
  227:     admin_username => {
  228:       type => 'username',  # Uses custom type definition
  229:       min => 5,            # Overrides custom type's min value
  230:       max => 15            # Overrides custom type's max value
  231:     }
  232:   };
  233: 
  234: Custom types work seamlessly with nested schema, optional parameters, and all other validation features.
  235: 
  236: =back
  237: 
  238: The schema can define the following rules for each parameter:
  239: 
  240: =over 4
  241: 
  242: =item * C<type>
  243: 
  244: The data type of the parameter.
  245: Valid types are C<string>, C<integer>, C<number>, C<float> C<boolean>, C<scalar>, C<scalarref>, C<stringref>, C<hashref>, C<arrayref>, C<object>, C<coderef> and C<void>.
  246: C<scalar> accepts any plain scalar value (string, number, boolean, etc.) but rejects references (arrayrefs, hashrefs, coderefs, objects).
  247: C<scalarref> accepts a reference to a scalar value (e.g. C<\$var>) but rejects plain scalars, arrayrefs, hashrefs, coderefs, and objects.
  248: C<stringref> accepts a reference to a scalar that contains a plain string (e.g. C<\$str>) and rejects plain scalars, references-to-references, arrayrefs, hashrefs, coderefs, and objects.
  249: C<void> asserts that the parameter value is C<undef> (the parameter represents a void return or absent output).
  250: When C<void> is used the schema must contain exactly one parameter.
  251: The C<min>/C<max> constraints apply to the B<length> (in characters) of the referenced string.
  252: All other string rules (C<matches>, C<nomatch>, C<memberof>, etc.) operate on the dereferenced string value.
  253: The validated return value is the dereferenced plain string.
  254: 
  255: A type can be an arrayref when a parameter could have different types (e.g. a string or an object).
  256: 
  257:   $schema = {
  258:     username => [
  259:       { type => 'string', min => 3, max => 50 },	# Name
  260:       { type => 'integer', 'min' => 1 },	# UID that isn't root
  261:     ]
  262:   };
  263: 
  264: As a shorthand, C<type> itself may be an arrayref of type name strings (a I<union type>)
  265: when all other constraints are shared between the alternatives:
  266: 
  267:   $schema = {
  268:     data => { type => ['string', 'arrayref'] },
  269:     id   => { type => ['string', 'integer'], optional => 1 },
  270:   };
  271: 
  272: This is equivalent to the full array-of-rules form but more concise.
  273: Every other key in the rule hash (C<optional>, C<min>, C<max>, C<matches>, etc.)
  274: is inherited by each candidate type and validated independently against it.
  275: Type names are tried left-to-right; the first match wins and its coercion
  276: (e.g. numeric types) is propagated back to the caller.
  277: If the value fails all candidate types, validation croaks with a message
  278: listing the union members.
  279: 
  280: =item * C<can>
  281: 
  282: The parameter must be an object that understands the method C<can>.
  283: C<can> can be a simple scalar string of a method name,
  284: or an arrayref of a list of method names, all of which must be supported by the object.
  285: 
  286:    $schema = {
  287:      gedcom => { type => object, can => 'get_individual' }
  288:    }
  289: 
  290: =item * C<isa>
  291: 
  292: The parameter must be an object of type C<isa>.
  293: 
  294: =item * C<memberof>
  295: 
  296: The parameter must be a member of the given arrayref.
  297: 
  298:   status => {
  299:     type => 'string',
  300:     memberof => ['draft', 'published', 'archived']
  301:   }
  302: 
  303:   priority => {
  304:     type => 'integer',
  305:     memberof => [1, 2, 3, 4, 5]
  306:   }
  307: 
  308: For string types, the comparison is case-sensitive by default. Use the C<case_sensitive>
  309: flag to control this behavior:
  310: 
  311:   # Case-sensitive (default) - must be exact match
  312:   code => {
  313:     type => 'string',
  314:     memberof => ['ABC', 'DEF', 'GHI']
  315:     # 'abc' will fail
  316:   }
  317: 
  318:   # Case-insensitive - any case accepted
  319:   code => {
  320:     type => 'string',
  321:     memberof => ['ABC', 'DEF', 'GHI'],
  322:     case_sensitive => 0
  323:     # 'abc', 'Abc', 'ABC' all pass, original case preserved
  324:   }
  325: 
  326: For numeric types (C<integer>, C<number>, C<float>), the comparison uses numeric
  327: equality (C<==> operator):
  328: 
  329:   rating => {
  330:     type => 'number',
  331:     memberof => [0.5, 1.0, 1.5, 2.0]
  332:   }
  333: 
  334: Note that C<memberof> cannot be combined with C<min> or C<max> constraints as they
  335: serve conflicting purposes - C<memberof> defines an explicit whitelist while C<min>/C<max>
  336: define ranges.
  337: 
  338: =item * C<enum>
  339: 
  340: Same as C<memberof>.
  341: 
  342: =item * C<values>
  343: 
  344: Same as C<memberof>.
  345: 
  346: =item * C<notmemberof>
  347: 
  348: The parameter must not be a member of the given arrayref (blacklist).
  349: This is the inverse of C<memberof>.
  350: 
  351:   username => {
  352:     type => 'string',
  353:     notmemberof => ['admin', 'root', 'system', 'administrator']
  354:   }
  355: 
  356:   port => {
  357:     type => 'integer',
  358:     notmemberof => [22, 23, 25, 80, 443]  # Reserved ports
  359:   }
  360: 
  361: Like C<memberof>, string comparisons are case-sensitive by default but can be controlled
  362: with the C<case_sensitive> flag:
  363: 
  364:   # Case-sensitive (default)
  365:   username => {
  366:     type => 'string',
  367:     notmemberof => ['Admin', 'Root']
  368:     # 'admin' would pass, 'Admin' would fail
  369:   }
  370: 
  371:   # Case-insensitive
  372:   username => {
  373:     type => 'string',
  374:     notmemberof => ['Admin', 'Root'],
  375:     case_sensitive => 0
  376:     # 'admin', 'ADMIN', 'Admin' all fail
  377:   }
  378: 
  379: The blacklist is checked after any C<transform> rules are applied, allowing you to
  380: normalize input before checking:
  381: 
  382:   username => {
  383:     type => 'string',
  384:     transform => sub { lc($_[0]) },  # Normalize to lowercase
  385:     notmemberof => ['admin', 'root', 'system']
  386:   }
  387: 
  388: C<notmemberof> can be combined with other validation rules:
  389: 
  390:   username => {
  391:     type => 'string',
  392:     notmemberof => ['admin', 'root', 'system'],
  393:     min => 3,
  394:     max => 20,
  395:     matches => qr/^[a-z0-9_]+$/
  396:   }
  397: 
  398: =item * C<case_sensitive>
  399: 
  400: A boolean value indicating whether string comparisons should be case-sensitive.
  401: This flag affects the C<memberof> and C<notmemberof> validation rules.
  402: The default value is C<1> (case-sensitive).
  403: 
  404: When set to C<0>, string comparisons are performed case-insensitively, allowing values
  405: with different casing to match. The original case of the input value is preserved in
  406: the validated output.
  407: 
  408:   # Case-sensitive (default)
  409:   status => {
  410:     type => 'string',
  411:     memberof => ['Draft', 'Published', 'Archived'] # Input 'draft' will fail - must match exact case
  412:   }
  413: 
  414:   # Case-insensitive
  415:   status => {
  416:     type => 'string',
  417:     memberof => ['Draft', 'Published', 'Archived'],
  418:     case_sensitive => 0 # Input 'draft', 'DRAFT', or 'DrAfT' will all pass
  419:   }
  420: 
  421:   country_code => {
  422:     type => 'string',
  423:     memberof => ['US', 'UK', 'CA', 'FR'],
  424:     case_sensitive => 0  # Accept 'us', 'US', 'Us', etc.
  425:   }
  426: 
  427: This flag has no effect on numeric types (C<integer>, C<number>, C<float>) as numbers
  428: do not have case.
  429: 
  430: =item * C<min>/C<minimum>
  431: 
  432: The minimum length (for strings in characters not bytes), value (for numbers) or number of keys (for hashrefs).
  433: 
  434: =item * C<max>
  435: 
  436: The maximum length (for strings in characters not bytes), value (for numbers) or number of keys (for hashrefs).
  437: 
  438: =item * C<matches>
  439: 
  440: A regular expression that the parameter value must match.
  441: Checks all members of arrayrefs.
  442: 
  443: =item * C<nomatch>
  444: 
  445: A regular expression that the parameter value must not match.
  446: Checks all members of arrayrefs.
  447: 
  448: =item * C<position>
  449: 
  450: For routines and methods that take positional args,
  451: this integer value defines which position the argument will be in.
  452: If this is set for all arguments,
  453: C<validate_strict> will return a reference to an array, rather than a reference to a hash.
  454: 
  455: =item * C<regex>
  456: 
  457: Synonym of matches
  458: 
  459: =item * C<description>
  460: 
  461: The description of the rule
  462: 
  463: =item * C<callback>
  464: 
  465: A code reference to a subroutine that performs custom validation logic.
  466: The subroutine should accept the parameter value, the argument list and the schema as arguments and return true if the value is valid, false otherwise.
  467: 
  468: Use this to test more complex examples:
  469: 
  470:   my $schema = {
  471:     even_number => {
  472:       type => 'integer',
  473:       callback => sub { $_[0] % 2 == 0 }
  474:   };
  475: 
  476:   # Specify the arguments for a routine which has a second, optional argument, which, if given, must be less than or equal to the first
  477:   my $schema = {
  478:     first => {
  479:       type => 'integer'
  480:     }, second => {
  481:       type => 'integer',
  482:       optional => 1,
  483:       callback => sub {
  484:         my($value, $args) = @_;
  485: 	# The 'defined' is needed in case 'second' is evaluated before 'first'
  486: 	return (defined($args->{first}) && $value <= $args->{first}) ? 1 : 0
  487:       }
  488:     }
  489:   };
  490: 
  491: =item * C<optional>
  492: 
  493: A boolean value indicating whether the parameter is optional.
  494: If true, the parameter is not required.
  495: If false or omitted, the parameter is required.
  496: 
  497: It can be a reference to a code snippet that will return true or false,
  498: to determine if the parameter is optional or not.
  499: The code will be called with two arguments: the value of the parameter and hash ref of all parameters:
  500: 
  501:   my $schema = {
  502:     optional_field => {
  503:       type => 'string',
  504:       optional => sub {
  505:         my ($value, $all_params) = @_;
  506:         return $all_params->{make_optional} ? 1 : 0;
  507:       }
  508:     },
  509:     make_optional => { type => 'boolean' }
  510:   };
  511: 
  512:   my $result = validate_strict(schema => $schema, input => { make_optional => 1 });
  513: 
  514: If the parameter is not optional, it can be passed an undef value, which will not flag an error.
  515: This is by design.
  516: So this will not say that the required parameter 's' is missing:
  517: 
  518:     validate_strict(
  519:         schema => { s => { type => 'string' } },
  520:         input  => { s => undef },
  521:     );
  522: 
  523: =item * C<default>
  524: 
  525: Populate missing optional parameters with the specified value.
  526: Note that this value is not validated.
  527: 
  528:   username => {
  529:     type => 'string',
  530:     optional => 1,
  531:     default => 'guest'
  532:   }
  533: 
  534: =item * C<element_type>
  535: 
  536: Extends the validation to individual elements of arrays.
  537: 
  538:   tags => {
  539:     type => 'arrayref',
  540:     element_type => 'number',	# Float means the same
  541:     min => 1,	# this is the length of the array, not the min value for each of the numbers. For that, add a C<schema> rule
  542:     max => 5
  543:   }
  544: 
  545: =item * C<error_msg>
  546: 
  547: The custom error message to be used in the event of a validation failure.
  548: 
  549:   age => {
  550:     type => 'integer',
  551:     min => 18,
  552:     error_msg => 'You must be at least 18 years old'
  553:   }
  554: 
  555: =item * C<nullable>
  556: 
  557: Like optional,
  558: though this cannot be a coderef,
  559: only a flag.
  560: 
  561: =item * C<schema>
  562: 
  563: You can validate nested hashrefs and arrayrefs using the C<schema> property:
  564: 
  565:     my $schema = {
  566:         user => {	# 'user' is a hashref
  567:             type => 'hashref',
  568:             schema => {	# Specify what the elements of the hash should be
  569:                 name => { type => 'string' },
  570:                 age => { type => 'integer', min => 0 },
  571:                 hobbies => {	# 'hobbies' is an array ref that this user has

  574:                     min => 1 # At least one hobby
  575:                 }
  576:             }
  577:         }, metadata => {
  578:             type => 'hashref',
  579:             schema => {
  580:                 created => { type => 'string' },
  581:                 tags => {
  582:                     type => 'arrayref',
  583:                     schema => {
  584:                         type => 'string',
  585:                         matches => qr/^[a-z]+$/	# Or you can say matches => '^[a-z]+$'
  586:                     }
  587:                 }
  588:             }
  589:         }
  590:     };
  591: 
  592: =item * C<validate>
  593: 
  594: A snippet of code that validates the input.
  595: It's passed the input arguments,
  596: and return a string containing a reason for rejection,
  597: or undef if it's allowed.
  598: 
  599:     my $schema = {
  600:       user => {
  601:         type => 'string',
  602: 	validate => sub {
  603: 	  if($_[0]->{'password'} eq 'bar') {
  604: 	    return undef;
  605: 	  }
  606: 	  return 'Invalid password, try again';
  607: 	}
  608:       }, password => {
  609:          type => 'string'
  610:       }
  611:     };
  612: 
  613: =item * C<transform>
  614: 
  615: A code reference to a subroutine that transforms/sanitizes the parameter value before validation.
  616: The subroutine should accept the parameter value as an argument and return the transformed value.
  617: The transformation is applied before any validation rules are checked, allowing you to normalize
  618: or clean data before it is validated.
  619: 
  620: Common use cases include trimming whitespace, normalizing case, formatting phone numbers,
  621: sanitizing user input, and converting between data formats.
  622: 
  623:   # Simple string transformations
  624:   username => {
  625:     type => 'string',
  626:     transform => sub { lc(trim($_[0])) },  # lowercase and trim
  627:     matches => qr/^[a-z0-9_]+$/
  628:   }
  629: 
  630:   email => {
  631:     type => 'string',
  632:     transform => sub { lc(trim($_[0])) },  # normalize email
  633:     matches => qr/^[^@\s]+\@[^@\s]+\.[^@\s]+$/
  634:   }
  635: 
  636:   # Array transformations
  637:   tags => {
  638:     type => 'arrayref',
  639:     transform => sub { [map { lc($_) } @{$_[0]}] },  # lowercase all elements
  640:     element_type => 'string'
  641:   }
  642: 
  643:   keywords => {
  644:     type => 'arrayref',
  645:     transform => sub {
  646:       my @arr = map { lc(trim($_)) } @{$_[0]};
  647:       my %seen;
  648:       return [grep { !$seen{$_}++ } @arr];  # remove duplicates
  649:     }
  650:   }

  652:   # Numeric transformations
  653:   quantity => {
  654:     type => 'integer',
  655:     transform => sub { int($_[0] + 0.5) },  # round to nearest integer
  656:     min => 1
  657:   }

  659:   # Sanitization
  660:   slug => {
  661:     type => 'string',
  662:     transform => sub {

  665:       $str =~ s/\s+/-/g;      # replace spaces with hyphens
  666:       return $str;
  667:     },
  668:     matches => qr/^[a-z0-9-]+$/
  669:   }
  670: 
  671:   phone => {
  672:     type => 'string',
  673:     transform => sub {
  674:       my $str = $_[0];
  675:       $str =~ s/\D//g;  # remove all non-digits
  676:       return $str;
  677:     },

  681: The C<transform> function is applied to the value before any validation checks (C<min>/C<minimum>, C<max>,
  682: C<matches>, C<callback>, etc.), ensuring that validation rules are checked against the cleaned data.
  683: 
  684: Transformations work with all parameter types including nested structures:
  685: 
  686:   user => {
  687:     type => 'hashref',
  688:     schema => {
  689:       name => {

  691:         transform => sub { trim($_[0]) }

  694:         transform => sub { lc(trim($_[0])) }
  695:       }
  696:     }

  700: 
  701:   my $custom_types = {
  702:     email => {
  703:       type => 'string',
  704:       transform => sub { lc(trim($_[0])) },
  705:       matches => qr/^[^@\s]+\@[^@\s]+\.[^@\s]+$/

  707:   };

  709: Note that the transformed value is what gets returned in the validated result and is what
  710: subsequent validation rules will check against. If a transformation might fail, ensure it
  711: handles edge cases appropriately.
  712: It is the responsibility of the transformer to ensure that the type of the returned value is correct,
  713: since that is what will be validated.
  714: 
  715: Many validators also allow a code ref to be passed so that you can create your own, conditional validation rule, e.g.:
  716: 
  717:   $schema = {
  718:     age => {
  719:       type => 'integer',
  720:       min => sub {

  723:       }
  724:     }
  725:   }

  727: =item * C<validator>
  728: 
  729: A synonym of C<validate>, for compatibility with L<Data::Processor>.
  730: 
  731: =item * C<cross_validation>
  732: 
  733: A reference to a hash that defines validation rules that depend on more than one parameter.
  734: Cross-field validations are performed after all individual parameter validations have passed,
  735: allowing you to enforce business logic that requires checking relationships between different fields.
  736: 
  737: Each cross-validation rule is a key-value pair where the key is a descriptive name for the validation
  738: and the value is a code reference that accepts a hash reference of all validated parameters.
  739: The subroutine should return C<undef> if the validation passes, or an error message string if it fails.
  740: 
  741:   my $schema = {
  742:     password => { type => 'string', min => 8 },
  743:     password_confirm => { type => 'string' }
  744:   };
  745: 
  746:   my $cross_validation = {
  747:     passwords_match => sub {
  748:       my $params = shift;
  749:       return $params->{password} eq $params->{password_confirm}
  750:         ? undef : "Passwords don't match";
  751:     }
  752:   };
  753: 
  754:   my $validated = validate_strict(
  755:     schema => $schema,
  756:     input => $input,
  757:     cross_validation => $cross_validation
  758:   );
  759: 
  760: Common use cases include password confirmation, date range validation, numeric comparisons,
  761: and conditional requirements:
  762: 
  763:   # Date range validation
  764:   my $cross_validation = {
  765:     date_range_valid => sub {
  766:       my $params = shift;
  767:       return $params->{start_date} le $params->{end_date}
  768:         ? undef : "Start date must be before or equal to end date";
  769:     }
  770:   };
  771: 
  772:   # Price range validation
  773:   my $cross_validation = {
  774:     price_range_valid => sub {
  775:       my $params = shift;
  776:       return $params->{min_price} <= $params->{max_price}
  777:         ? undef : "Minimum price must be less than or equal to maximum price";
  778:     }
  779:   };
  780: 
  781:   # Conditional required field
  782:   my $cross_validation = {
  783:     address_required_for_delivery => sub {
  784:       my $params = shift;
  785:       if ($params->{shipping_method} eq 'delivery' && !$params->{delivery_address}) {
  786:         return "Delivery address is required when shipping method is 'delivery'";
  787:       }
  788:       return undef;
  789:     }
  790:   };
  791: 
  792: Multiple cross-validations can be defined in the same hash, and they are all checked in order.
  793: If any cross-validation fails, the function will C<croak> with the error message returned by the validation:
  794: 
  795:   my $cross_validation = {
  796:     passwords_match => sub {
  797:       my $params = shift;
  798:       return $params->{password} eq $params->{password_confirm}
  799:         ? undef : "Passwords don't match";
  800:     },
  801:     emails_match => sub {
  802:       my $params = shift;
  803:       return $params->{email} eq $params->{email_confirm}
  804:         ? undef : "Email addresses don't match";
  805:     },
  806:     age_matches_birth_year => sub {
  807:       my $params = shift;
  808:       my $current_year = (localtime)[5] + 1900;
  809:       my $calculated_age = $current_year - $params->{birth_year};
  810:       return abs($calculated_age - $params->{age}) <= 1
  811:         ? undef : "Age doesn't match birth year";
  812:     }
  813:   };
  814: 
  815: Cross-validations receive the parameters after individual validation and transformation have been applied,
  816: so you can rely on the data being in the correct format and type:
  817: 
  818:   my $schema = {
  819:     email => {
  820:       type => 'string',
  821:       transform => sub { lc($_[0]) }  # Lowercased before cross-validation
  822:     },
  823:     email_confirm => {
  824:       type => 'string',
  825:       transform => sub { lc($_[0]) }

  827:   };

  835:     }

  838: Cross-validations can access nested structures and optional fields:
  839: 
  840:   my $cross_validation = {
  841:     guardian_required_for_minors => sub {
  842:       my $params = shift;

  874: =item * C<relationships>
  875: 
  876: A reference to an array that defines validation rules based on relationships between parameters.
  877: Relationship validations are performed after all individual parameter validations have passed,
  878: but before cross-validations.
  879: 
  880: Each relationship is a hash reference with a C<type> field and additional fields depending on the type:
  881: 
  882: =over 4
  883: 
  884: =item * B<mutually_exclusive>
  885: 
  886: Parameters that cannot be specified together.
  887: 
  888:   relationships => [
  889:     {
  890:       type => 'mutually_exclusive',
  891:       params => ['file', 'content'],
  892:       description => 'Cannot specify both file and content'
  893:     }
  894:   ]
  895: 
  896: =item * B<required_group>
  897: 
  898: At least one parameter from the group must be specified.
  899: 
  900:   relationships => [
  901:     {
  902:       type => 'required_group',
  903:       params => ['id', 'name'],
  904:       logic => 'or',
  905:       description => 'Must specify either id or name'
  906:     }
  907:   ]
  908: 
  909: =item * B<conditional_requirement>
  910: 
  911: If one parameter is specified, another becomes required.
  912: 
  913:   relationships => [
  914:     {
  915:       type => 'conditional_requirement',
  916:       if => 'async',
  917:       then_required => 'callback',
  918:       description => 'When async is specified, callback is required'
  919:     }
  920:   ]
  921: 
  922: =item * B<dependency>
  923: 
  924: One parameter requires another to be present.
  925: 
  926:   relationships => [
  927:     {
  928:       type => 'dependency',
  929:       param => 'port',
  930:       requires => 'host',
  931:       description => 'port requires host to be specified'
  932:     }
  933:   ]
  934: 
  935: =item * B<value_constraint>
  936: 
  937: Specific value requirements between parameters.
  938: 
  939:   relationships => [
  940:     {
  941:       type => 'value_constraint',
  942:       if => 'ssl',
  943:       then => 'port',
  944:       operator => '==',
  945:       value => 443,
  946:       description => 'When ssl is specified, port must equal 443'
  947:     }
  948:   ]
  949: 
  950: =item * B<value_conditional>
  951: 
  952: Parameter required when another has a specific value.
  953: 
  954:   relationships => [
  955:     {
  956:       type => 'value_conditional',
  957:       if => 'mode',
  958:       equals => 'secure',
  959:       then_required => 'key',
  960:       description => "When mode equals 'secure', key is required"
  961:     }
  962:   ]
  963: 
  964: =back
  965: 
  966: If a parameter is optional and its value is C<undef>,
  967: validation will be skipped for that parameter.
  968: 
  969: If the validation fails, the function will C<croak> with an error message describing the validation failure.
  970: 
  971: If the validation is successful, the function will return a reference to a new hash containing the validated and (where applicable) coerced parameters.  Integer and number parameters will be coerced to their respective types.
  972: 
  973: The C<description> field is optional but recommended for clearer error messages.
  974: 
  975: =back
