   87: =head2 validate_strict
   88: 
   89: Validates a set of parameters against a schema.
   90: 
   91: This function takes two mandatory arguments:
   92: 
   93: =over 4
   94: 
   95: =item * C<schema> || C<members>
   96: 
   97: A reference to a hash that defines the validation rules for each parameter.
   98: The keys of the hash are the parameter names, and the values are either a string representing the parameter type or a reference to a hash containing more detailed rules.
   99: 
  100: As an alternative the schema may be supplied as an B<arrayref of parameter hashrefs>,
  101: where every element describes one parameter and carries a mandatory
  102: C<name> key:
  103: 
  104:   $schema = [
  105:     { name => 'username', type => 'string', min => 3, max => 50 },
  106:     { name => 'age',      type => 'integer', min => 0, max => 150 },
  107:     { name => 'role',     type => 'string', optional => 1, default => 'user' },
  108:   ];
  109: 
  110: The arrayref form is normalised to the standard hashref form before any further
  111: processing.  It is particularly useful when declaration order matters (e.g.
  112: for positional or mixed calling conventions used by some CPAN modules).  The
  113: C<name> key is consumed during normalisation and does not appear as a
  114: validation rule.
  115: 
  116: For some sort of compatibility with L<Data::Processor>,
  117: it is possible to wrap the schema within a hash like this:
  118: 
  119:   $schema = {
  120:     description => 'Describe what this schema does',
  121:     error_msg => 'An error message',
  122:     schema => {
  123:       # ... schema goes here
  124:     }
  125:   }
  126: 
  127: =item * C<args> || C<input>
  128: 
  129: A reference to a hash containing the parameters to be validated.
  130: The keys of the hash are the parameter names, and the values are the parameter values.
  131: 
  132: =back
  133: 
  134: It takes optional arguments:
  135: 
  136: =over 4
  137: 
  138: =item * C<description>
  139: 
  140: What the schema does,
  141: used in error messages.
  142: 
  143: =item * C<error_msg>
  144: 
  145: Overrides the default message when something doesn't validate.
  146: 
  147: =item * C<unknown_parameter_handler>
  148: 
  149: This parameter describes what to do when a parameter is given that is not in the schema of valid parameters.
  150: It must be one of C<die>, C<warn>, or C<ignore>.
  151: 
  152: It defaults to C<die> unless C<carp_on_warn> is given, in which case it defaults to C<warn>.
  153: 
  154: =item * C<logger>
  155: 
  156: A logging object that understands messages such as C<error> and C<warn>.
  157: 
  158: =item * C<custom_types>
  159: 
  160: A reference to a hash that defines reusable custom types.
  161: Custom types allow you to define validation rules once and reuse them throughout your schema,
  162: making your validation logic more maintainable and readable.
  163: 
  164: Each custom type is defined as a hash reference containing the same validation rules available for regular parameters
  165: (C<type>, C<min>, C<max>, C<matches>, C<memberof>, C<values>, C<enum>, C<notmemberof>, C<callback>, etc.).
  166: 
  167:   my $custom_types = {
  168:     email => {
  169:       type => 'string',
  170:       matches => qr/^[^@\s]+\@[^@\s]+\.[^@\s]+$/,
  171:       error_msg => 'Invalid email address format'
  172:     }, phone => {
  173:       type => 'string',
  174:       matches => qr/^\+?[1-9]\d{1,14}$/,
  175:       min => 10,
  176:       max => 15
  177:     }, percentage => {
  178:       type => 'number',
  179:       min => 0,
  180:       max => 100
  181:     }, status => {
  182:       type => 'string',
  183:       memberof => ['draft', 'published', 'archived']
  184:     }
  185:   };
  186: 
  187:   my $schema = {
  188:     user_email => { type => 'email' },
  189:     contact_number => { type => 'phone', optional => 1 },
  190:     completion => { type => 'percentage' },
  191:     post_status => { type => 'status' }
  192:   };
  193: 
  194:   my $validated = validate_strict(
  195:     schema => $schema,
  196:     input => $input,
  197:     custom_types => $custom_types
  198:   );
  199: 
  200: Custom types can be extended or overridden in the schema by specifying additional constraints:
  201: 
  202:   my $schema = {
  203:     admin_username => {
  204:       type => 'username',  # Uses custom type definition
  205:       min => 5,            # Overrides custom type's min value
  206:       max => 15            # Overrides custom type's max value
  207:     }
  208:   };
  209: 
  210: Custom types work seamlessly with nested schema, optional parameters, and all other validation features.
  211: 
  212: =back
  213: 
  214: The schema can define the following rules for each parameter:
  215: 
  216: =over 4
  217: 
  218: =item * C<type>
  219: 
  220: The data type of the parameter.
  221: Valid types are C<string>, C<integer>, C<number>, C<float> C<boolean>, C<scalar>, C<scalarref>, C<stringref>, C<hashref>, C<arrayref>, C<object>, C<coderef> and C<void>.
  222: C<scalar> accepts any plain scalar value (string, number, boolean, etc.) but rejects references (arrayrefs, hashrefs, coderefs, objects).
  223: C<scalarref> accepts a reference to a scalar value (e.g. C<\$var>) but rejects plain scalars, arrayrefs, hashrefs, coderefs, and objects.
  224: C<stringref> accepts a reference to a scalar that contains a plain string (e.g. C<\$str>) and rejects plain scalars, references-to-references, arrayrefs, hashrefs, coderefs, and objects.
  225: C<void> asserts that the parameter value is C<undef> (the parameter represents a void return or absent output).
  226: When C<void> is used the schema must contain exactly one parameter.
  227: The C<min>/C<max> constraints apply to the B<length> (in characters) of the referenced string.
  228: All other string rules (C<matches>, C<nomatch>, C<memberof>, etc.) operate on the dereferenced string value.
  229: The validated return value is the dereferenced plain string.
  230: 
  231: A type can be an arrayref when a parameter could have different types (e.g. a string or an object).
  232: 
  233:   $schema = {
  234:     username => [
  235:       { type => 'string', min => 3, max => 50 },	# Name
  236:       { type => 'integer', 'min' => 1 },	# UID that isn't root
  237:     ]
  238:   };
  239: 
  240: As a shorthand, C<type> itself may be an arrayref of type name strings (a I<union type>)
  241: when all other constraints are shared between the alternatives:
  242: 
  243:   $schema = {
  244:     data => { type => ['string', 'arrayref'] },
  245:     id   => { type => ['string', 'integer'], optional => 1 },
  246:   };
  247: 
  248: This is equivalent to the full array-of-rules form but more concise.
  249: Every other key in the rule hash (C<optional>, C<min>, C<max>, C<matches>, etc.)
  250: is inherited by each candidate type and validated independently against it.
  251: Type names are tried left-to-right; the first match wins and its coercion
  252: (e.g. numeric types) is propagated back to the caller.
  253: If the value fails all candidate types, validation croaks with a message
  254: listing the union members.
  255: 
  256: =item * C<can>
  257: 
  258: The parameter must be an object that understands the method C<can>.
  259: C<can> can be a simple scalar string of a method name,
  260: or an arrayref of a list of method names, all of which must be supported by the object.
  261: 
  262:    $schema = {
  263:      gedcom => { type => object, can => 'get_individual' }
  264:    }
  265: 
  266: =item * C<isa>
  267: 
  268: The parameter must be an object of type C<isa>.
  269: 
  270: =item * C<memberof>
  271: 
  272: The parameter must be a member of the given arrayref.
  273: 
  274:   status => {
  275:     type => 'string',
  276:     memberof => ['draft', 'published', 'archived']
  277:   }
  278: 
  279:   priority => {
  280:     type => 'integer',
  281:     memberof => [1, 2, 3, 4, 5]
  282:   }
  283: 
  284: For string types, the comparison is case-sensitive by default. Use the C<case_sensitive>
  285: flag to control this behavior:
  286: 
  287:   # Case-sensitive (default) - must be exact match
  288:   code => {
  289:     type => 'string',
  290:     memberof => ['ABC', 'DEF', 'GHI']
  291:     # 'abc' will fail
  292:   }
  293: 
  294:   # Case-insensitive - any case accepted
  295:   code => {
  296:     type => 'string',
  297:     memberof => ['ABC', 'DEF', 'GHI'],
  298:     case_sensitive => 0
  299:     # 'abc', 'Abc', 'ABC' all pass, original case preserved
  300:   }
  301: 
  302: For numeric types (C<integer>, C<number>, C<float>), the comparison uses numeric
  303: equality (C<==> operator):
  304: 
  305:   rating => {
  306:     type => 'number',
  307:     memberof => [0.5, 1.0, 1.5, 2.0]
  308:   }
  309: 
  310: Note that C<memberof> cannot be combined with C<min> or C<max> constraints as they
  311: serve conflicting purposes - C<memberof> defines an explicit whitelist while C<min>/C<max>
  312: define ranges.
  313: 
  314: =item * C<enum>
  315: 
  316: Same as C<memberof>.
  317: 
  318: =item * C<values>
  319: 
  320: Same as C<memberof>.
  321: 
  322: =item * C<notmemberof>
  323: 
  324: The parameter must not be a member of the given arrayref (blacklist).
  325: This is the inverse of C<memberof>.
  326: 
  327:   username => {
  328:     type => 'string',
  329:     notmemberof => ['admin', 'root', 'system', 'administrator']
  330:   }
  331: 
  332:   port => {
  333:     type => 'integer',
  334:     notmemberof => [22, 23, 25, 80, 443]  # Reserved ports
  335:   }
  336: 
  337: Like C<memberof>, string comparisons are case-sensitive by default but can be controlled
  338: with the C<case_sensitive> flag:
  339: 
  340:   # Case-sensitive (default)
  341:   username => {
  342:     type => 'string',
  343:     notmemberof => ['Admin', 'Root']
  344:     # 'admin' would pass, 'Admin' would fail
  345:   }
  346: 
  347:   # Case-insensitive
  348:   username => {
  349:     type => 'string',
  350:     notmemberof => ['Admin', 'Root'],
  351:     case_sensitive => 0
  352:     # 'admin', 'ADMIN', 'Admin' all fail
  353:   }
  354: 
  355: The blacklist is checked after any C<transform> rules are applied, allowing you to
  356: normalize input before checking:
  357: 
  358:   username => {
  359:     type => 'string',
  360:     transform => sub { lc($_[0]) },  # Normalize to lowercase
  361:     notmemberof => ['admin', 'root', 'system']
  362:   }
  363: 
  364: C<notmemberof> can be combined with other validation rules:
  365: 
  366:   username => {
  367:     type => 'string',
  368:     notmemberof => ['admin', 'root', 'system'],
  369:     min => 3,
  370:     max => 20,
  371:     matches => qr/^[a-z0-9_]+$/
  372:   }
  373: 
  374: =item * C<case_sensitive>
  375: 
  376: A boolean value indicating whether string comparisons should be case-sensitive.
  377: This flag affects the C<memberof> and C<notmemberof> validation rules.
  378: The default value is C<1> (case-sensitive).
  379: 
  380: When set to C<0>, string comparisons are performed case-insensitively, allowing values
  381: with different casing to match. The original case of the input value is preserved in
  382: the validated output.
  383: 
  384:   # Case-sensitive (default)
  385:   status => {
  386:     type => 'string',
  387:     memberof => ['Draft', 'Published', 'Archived'] # Input 'draft' will fail - must match exact case
  388:   }
  389: 
  390:   # Case-insensitive
  391:   status => {
  392:     type => 'string',
  393:     memberof => ['Draft', 'Published', 'Archived'],
  394:     case_sensitive => 0 # Input 'draft', 'DRAFT', or 'DrAfT' will all pass
  395:   }
  396: 
  397:   country_code => {
  398:     type => 'string',
  399:     memberof => ['US', 'UK', 'CA', 'FR'],
  400:     case_sensitive => 0  # Accept 'us', 'US', 'Us', etc.
  401:   }
  402: 
  403: This flag has no effect on numeric types (C<integer>, C<number>, C<float>) as numbers
  404: do not have case.
  405: 
  406: =item * C<min>/C<minimum>
  407: 
  408: The minimum length (for strings in characters not bytes), value (for numbers) or number of keys (for hashrefs).
  409: 
  410: =item * C<max>
  411: 
  412: The maximum length (for strings in characters not bytes), value (for numbers) or number of keys (for hashrefs).
  413: 
  414: =item * C<matches>
  415: 
  416: A regular expression that the parameter value must match.
  417: Checks all members of arrayrefs.
  418: 
  419: =item * C<nomatch>
  420: 
  421: A regular expression that the parameter value must not match.
  422: Checks all members of arrayrefs.
  423: 
  424: =item * C<position>
  425: 
  426: For routines and methods that take positional args,
  427: this integer value defines which position the argument will be in.
  428: If this is set for all arguments,
  429: C<validate_strict> will return a reference to an array, rather than a reference to a hash.
  430: 
  431: =item * C<regex>
  432: 
  433: Synonym of matches
  434: 
  435: =item * C<description>
  436: 
  437: The description of the rule
  438: 
  439: =item * C<callback>
  440: 
  441: A code reference to a subroutine that performs custom validation logic.
  442: The subroutine should accept the parameter value, the argument list and the schema as arguments and return true if the value is valid, false otherwise.
  443: 
  444: Use this to test more complex examples:
  445: 
  446:   my $schema = {
  447:     even_number => {
  448:       type => 'integer',
  449:       callback => sub { $_[0] % 2 == 0 }
  450:   };
  451: 
  452:   # Specify the arguments for a routine which has a second, optional argument, which, if given, must be less than or equal to the first
  453:   my $schema = {
  454:     first => {
  455:       type => 'integer'
  456:     }, second => {
  457:       type => 'integer',
  458:       optional => 1,
  459:       callback => sub {
  460:         my($value, $args) = @_;
  461: 	# The 'defined' is needed in case 'second' is evaluated before 'first'
  462: 	return (defined($args->{first}) && $value <= $args->{first}) ? 1 : 0
  463:       }
  464:     }
  465:   };
  466: 
  467: =item * C<optional>
  468: 
  469: A boolean value indicating whether the parameter is optional.
  470: If true, the parameter is not required.
  471: If false or omitted, the parameter is required.
  472: 
  473: It can be a reference to a code snippet that will return true or false,
  474: to determine if the parameter is optional or not.
  475: The code will be called with two arguments: the value of the parameter and hash ref of all parameters:
  476: 
  477:   my $schema = {
  478:     optional_field => {
  479:       type => 'string',
  480:       optional => sub {
  481:         my ($value, $all_params) = @_;
  482:         return $all_params->{make_optional} ? 1 : 0;
  483:       }
  484:     },
  485:     make_optional => { type => 'boolean' }
  486:   };
  487: 
  488:   my $result = validate_strict(schema => $schema, input => { make_optional => 1 });
  489: 
  490: If the parameter is not optional, it can be passed an undef value, which will not flag an error.
  491: This is by design.
  492: So this will not say that the required parameter 's' is missing:
  493: 
  494:     validate_strict(
  495:         schema => { s => { type => 'string' } },
  496:         input  => { s => undef },
  497:     );
  498: 
  499: =item * C<default>
  500: 
  501: Populate missing optional parameters with the specified value.
  502: Note that this value is not validated.
  503: 
  504:   username => {
  505:     type => 'string',
  506:     optional => 1,
  507:     default => 'guest'
  508:   }
  509: 
  510: =item * C<element_type>
  511: 
  512: Extends the validation to individual elements of arrays.
  513: 
  514:   tags => {
  515:     type => 'arrayref',
  516:     element_type => 'number',	# Float means the same
  517:     min => 1,	# this is the length of the array, not the min value for each of the numbers. For that, add a C<schema> rule
  518:     max => 5
  519:   }
  520: 
  521: =item * C<error_msg>
  522: 
  523: The custom error message to be used in the event of a validation failure.
  524: 
  525:   age => {
  526:     type => 'integer',
  527:     min => 18,
  528:     error_msg => 'You must be at least 18 years old'
  529:   }
  530: 
  531: =item * C<nullable>
  532: 
  533: Like optional,
  534: though this cannot be a coderef,
  535: only a flag.
  536: 
  537: =item * C<schema>
  538: 
  539: You can validate nested hashrefs and arrayrefs using the C<schema> property:
  540: 
  541:     my $schema = {
  542:         user => {	# 'user' is a hashref
  543:             type => 'hashref',
  544:             schema => {	# Specify what the elements of the hash should be
  545:                 name => { type => 'string' },
  546:                 age => { type => 'integer', min => 0 },
  547:                 hobbies => {	# 'hobbies' is an array ref that this user has
  548:                     type => 'arrayref',
  549:                     schema => { type => 'string' }, # Validate each hobby
  550:                     min => 1 # At least one hobby
  551:                 }
  552:             }
  553:         }, metadata => {
  554:             type => 'hashref',
  555:             schema => {
  556:                 created => { type => 'string' },
  557:                 tags => {
  558:                     type => 'arrayref',
  559:                     schema => {
  560:                         type => 'string',
  561:                         matches => qr/^[a-z]+$/	# Or you can say matches => '^[a-z]+$'
  562:                     }
  563:                 }
  564:             }
  565:         }
  566:     };
  567: 
  568: =item * C<validate>
  569: 
  570: A snippet of code that validates the input.
  571: It's passed the input arguments,
  572: and return a string containing a reason for rejection,
  573: or undef if it's allowed.
  574: 
  575:     my $schema = {
  576:       user => {
  577:         type => 'string',
  578: 	validate => sub {
  579: 	  if($_[0]->{'password'} eq 'bar') {
  580: 	    return undef;
  581: 	  }
  582: 	  return 'Invalid password, try again';
  583: 	}
  584:       }, password => {
  585:          type => 'string'
  586:       }
  587:     };

  589: =item * C<transform>
  590: 
  591: A code reference to a subroutine that transforms/sanitizes the parameter value before validation.
  592: The subroutine should accept the parameter value as an argument and return the transformed value.
  593: The transformation is applied before any validation rules are checked, allowing you to normalize
  594: or clean data before it is validated.
  595: 
  596: Common use cases include trimming whitespace, normalizing case, formatting phone numbers,
  597: sanitizing user input, and converting between data formats.
  598: 
  599:   # Simple string transformations
  600:   username => {
  601:     type => 'string',
  602:     transform => sub { lc(trim($_[0])) },  # lowercase and trim
  603:     matches => qr/^[a-z0-9_]+$/
  604:   }
  605: 
  606:   email => {
  607:     type => 'string',
  608:     transform => sub { lc(trim($_[0])) },  # normalize email
  609:     matches => qr/^[^@\s]+\@[^@\s]+\.[^@\s]+$/
  610:   }
  611: 
  612:   # Array transformations
  613:   tags => {
  614:     type => 'arrayref',
  615:     transform => sub { [map { lc($_) } @{$_[0]}] },  # lowercase all elements
  616:     element_type => 'string'
  617:   }
  618: 
  619:   keywords => {
  620:     type => 'arrayref',
  621:     transform => sub {
  622:       my @arr = map { lc(trim($_)) } @{$_[0]};
  623:       my %seen;
  624:       return [grep { !$seen{$_}++ } @arr];  # remove duplicates
  625:     }
  626:   }
  627:

  703: =item * C<validator>
  704: 
  705: A synonym of C<validate>, for compatibility with L<Data::Processor>.
  706: 
  707: =item * C<cross_validation>
  708: 
  709: A reference to a hash that defines validation rules that depend on more than one parameter.
  710: Cross-field validations are performed after all individual parameter validations have passed,
  711: allowing you to enforce business logic that requires checking relationships between different fields.
  712: 
  713: Each cross-validation rule is a key-value pair where the key is a descriptive name for the validation
  714: and the value is a code reference that accepts a hash reference of all validated parameters.
  715: The subroutine should return C<undef> if the validation passes, or an error message string if it fails.
  716: 
  717:   my $schema = {
  718:     password => { type => 'string', min => 8 },
  719:     password_confirm => { type => 'string' }
  720:   };
  721: 
  722:   my $cross_validation = {
  723:     passwords_match => sub {
  724:       my $params = shift;
  725:       return $params->{password} eq $params->{password_confirm}
  726:         ? undef : "Passwords don't match";
  727:     }
  728:   };
  729: 
  730:   my $validated = validate_strict(
  731:     schema => $schema,
  732:     input => $input,
  733:     cross_validation => $cross_validation
  734:   );
  735: 
  736: Common use cases include password confirmation, date range validation, numeric comparisons,
  737: and conditional requirements:
  738: 
  739:   # Date range validation
  740:   my $cross_validation = {
  741:     date_range_valid => sub {
  742:       my $params = shift;
  743:       return $params->{start_date} le $params->{end_date}
  744:         ? undef : "Start date must be before or equal to end date";
  745:     }
  746:   };
  747: 
  748:   # Price range validation
  749:   my $cross_validation = {
  750:     price_range_valid => sub {
  751:       my $params = shift;
  752:       return $params->{min_price} <= $params->{max_price}
  753:         ? undef : "Minimum price must be less than or equal to maximum price";
  754:     }
  755:   };
  756: 
  757:   # Conditional required field
  758:   my $cross_validation = {
  759:     address_required_for_delivery => sub {
  760:       my $params = shift;
  761:       if ($params->{shipping_method} eq 'delivery' && !$params->{delivery_address}) {
  762:         return "Delivery address is required when shipping method is 'delivery'";
  763:       }
  764:       return undef;
  765:     }
  766:   };

  768: Multiple cross-validations can be defined in the same hash, and they are all checked in order.
  769: If any cross-validation fails, the function will C<croak> with the error message returned by the validation:
  770: 
  771:   my $cross_validation = {
  772:     passwords_match => sub {
  773:       my $params = shift;
  774:       return $params->{password} eq $params->{password_confirm}

  779:       return $params->{email} eq $params->{email_confirm}
  780:         ? undef : "Email addresses don't match";

  788:     }
  789:   };

  791: Cross-validations receive the parameters after individual validation and transformation have been applied,
  792: so you can rely on the data being in the correct format and type:

  794:   my $schema = {

  850: =item * C<relationships>
  851: 
  852: A reference to an array that defines validation rules based on relationships between parameters.
  853: Relationship validations are performed after all individual parameter validations have passed,
  854: but before cross-validations.
  855: 
  856: Each relationship is a hash reference with a C<type> field and additional fields depending on the type:
  857: 
  858: =over 4
  859: 
  860: =item * B<mutually_exclusive>
  861: 
  862: Parameters that cannot be specified together.
  863: 
  864:   relationships => [
  865:     {
  866:       type => 'mutually_exclusive',
  867:       params => ['file', 'content'],
  868:       description => 'Cannot specify both file and content'
  869:     }
  870:   ]
  871: 
  872: =item * B<required_group>
  873: 
  874: At least one parameter from the group must be specified.
  875: 
  876:   relationships => [
  877:     {
  878:       type => 'required_group',
  879:       params => ['id', 'name'],
  880:       logic => 'or',
  881:       description => 'Must specify either id or name'
  882:     }
  883:   ]
  884: 
  885: =item * B<conditional_requirement>
  886: 
  887: If one parameter is specified, another becomes required.
  888: 
  889:   relationships => [
  890:     {
  891:       type => 'conditional_requirement',
  892:       if => 'async',
  893:       then_required => 'callback',
  894:       description => 'When async is specified, callback is required'
  895:     }
  896:   ]
  897: 
  898: =item * B<dependency>
  899: 
  900: One parameter requires another to be present.
  901: 
  902:   relationships => [
  903:     {
  904:       type => 'dependency',
  905:       param => 'port',
  906:       requires => 'host',
  907:       description => 'port requires host to be specified'
  908:     }
  909:   ]
  910: 
  911: =item * B<value_constraint>
  912: 
  913: Specific value requirements between parameters.
  914: 
  915:   relationships => [
  916:     {
  917:       type => 'value_constraint',
  918:       if => 'ssl',
  919:       then => 'port',
  920:       operator => '==',
  921:       value => 443,
  922:       description => 'When ssl is specified, port must equal 443'
  923:     }
  924:   ]
  925: 
  926: =item * B<value_conditional>
  927: 
  928: Parameter required when another has a specific value.
  929: 
  930:   relationships => [
  931:     {
  932:       type => 'value_conditional',
  933:       if => 'mode',
  934:       equals => 'secure',
  935:       then_required => 'key',
  936:       description => "When mode equals 'secure', key is required"
  937:     }
  938:   ]
  939: 
  940: =back
  941: 
  942: If a parameter is optional and its value is C<undef>,
  943: validation will be skipped for that parameter.
  944: 
  945: If the validation fails, the function will C<croak> with an error message describing the validation failure.
  946: 
  947: If the validation is successful, the function will return a reference to a new hash containing the validated and (where applicable) coerced parameters.  Integer and number parameters will be coerced to their respective types.
  948: 
  949: The C<description> field is optional but recommended for clearer error messages.
  950: 
  951: =back
