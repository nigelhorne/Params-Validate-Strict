  108: =head1	METHODS
  109: 
  110: =head2 validate_strict
  111: 
  112: Validates a set of parameters against a schema.
  113: 
  114: This function takes two mandatory arguments:
  115: 
  116: =over 4
  117: 
  118: =item * C<schema> || C<members>
  119: 
  120: A reference to a hash that defines the validation rules for each parameter.
  121: The keys of the hash are the parameter names, and the values are either a string representing the parameter type or a reference to a hash containing more detailed rules.
  122: 
  123: As an alternative the schema may be supplied as an B<arrayref of parameter hashrefs>,
  124: where every element describes one parameter and carries a mandatory
  125: C<name> key:
  126: 
  127:   $schema = [
  128:     { name => 'username', type => 'string', min => 3, max => 50 },
  129:     { name => 'age',      type => 'integer', min => 0, max => 150 },
  130:     { name => 'role',     type => 'string', optional => 1, default => 'user' },
  131:   ];
  132: 
  133: The arrayref form is normalised to the standard hashref form before any further
  134: processing.  It is particularly useful when declaration order matters (e.g.
  135: for positional or mixed calling conventions used by some CPAN modules).  The
  136: C<name> key is consumed during normalisation and does not appear as a
  137: validation rule.
  138: 
  139: For some sort of compatibility with L<Data::Processor>,
  140: it is possible to wrap the schema within a hash like this:
  141: 
  142:   $schema = {
  143:     description => 'Describe what this schema does',
  144:     error_msg => 'An error message',
  145:     schema => {
  146:       # ... schema goes here
  147:     }
  148:   }
  149: 
  150: =item * C<args> || C<input>
  151: 
  152: A reference to a hash containing the parameters to be validated.
  153: The keys of the hash are the parameter names, and the values are the parameter values.
  154: 
  155: =back
  156: 
  157: It takes optional arguments:
  158: 
  159: =over 4
  160: 
  161: =item * C<description>
  162: 
  163: What the schema does,
  164: used in error messages.
  165: 
  166: =item * C<error_msg>
  167: 
  168: Overrides the default message when something doesn't validate.
  169: 
  170: =item * C<unknown_parameter_handler>
  171: 
  172: This parameter describes what to do when a parameter is given that is not in the schema of valid parameters.
  173: It must be one of C<die>, C<warn>, or C<ignore>.
  174: 
  175: It defaults to C<die> unless C<carp_on_warn> is given, in which case it defaults to C<warn>.
  176: 
  177: =item * C<logger>
  178: 
  179: A logging object that understands messages such as C<error> and C<warn>.
  180: 
  181: =item * C<custom_types>
  182: 
  183: A reference to a hash that defines reusable custom types.
  184: Custom types allow you to define validation rules once and reuse them throughout your schema,
  185: making your validation logic more maintainable and readable.
  186: 
  187: Each custom type is defined as a hash reference containing the same validation rules available for regular parameters
  188: (C<type>, C<min>, C<max>, C<matches>, C<memberof>, C<values>, C<enum>, C<notmemberof>, C<callback>, etc.).
  189: 
  190:   my $custom_types = {
  191:     email => {
  192:       type => 'string',
  193:       matches => qr/^[^@\s]+\@[^@\s]+\.[^@\s]+$/,
  194:       error_msg => 'Invalid email address format'
  195:     }, phone => {
  196:       type => 'string',
  197:       matches => qr/^\+?[1-9]\d{1,14}$/,
  198:       min => 10,
  199:       max => 15
  200:     }, percentage => {
  201:       type => 'number',
  202:       min => 0,
  203:       max => 100
  204:     }, status => {
  205:       type => 'string',
  206:       memberof => ['draft', 'published', 'archived']
  207:     }
  208:   };
  209: 
  210:   my $schema = {
  211:     user_email => { type => 'email' },
  212:     contact_number => { type => 'phone', optional => 1 },
  213:     completion => { type => 'percentage' },
  214:     post_status => { type => 'status' }
  215:   };
  216: 
  217:   my $validated = validate_strict(
  218:     schema => $schema,
  219:     input => $input,
  220:     custom_types => $custom_types
  221:   );
  222: 
  223: Custom types can be extended or overridden in the schema by specifying additional constraints:
  224: 
  225:   my $schema = {
  226:     admin_username => {
  227:       type => 'username',  # Uses custom type definition
  228:       min => 5,            # Overrides custom type's min value
  229:       max => 15            # Overrides custom type's max value
  230:     }
  231:   };
  232: 
  233: Custom types work seamlessly with nested schema, optional parameters, and all other validation features.
  234: 
  235: =back
  236: 
  237: The schema can define the following rules for each parameter:
  238: 
  239: =over 4
  240: 
  241: =item * C<type>
  242: 
  243: The data type of the parameter.
  244: Valid types are C<string>, C<integer>, C<number>, C<float> C<boolean>, C<scalar>, C<scalarref>, C<stringref>, C<hashref>, C<arrayref>, C<object>, C<coderef> and C<void>.
  245: C<scalar> accepts any plain scalar value (string, number, boolean, etc.) but rejects references (arrayrefs, hashrefs, coderefs, objects).
  246: C<scalarref> accepts a reference to a scalar value (e.g. C<\$var>) but rejects plain scalars, arrayrefs, hashrefs, coderefs, and objects.
  247: C<stringref> accepts a reference to a scalar that contains a plain string (e.g. C<\$str>) and rejects plain scalars, references-to-references, arrayrefs, hashrefs, coderefs, and objects.
  248: C<void> asserts that the parameter value is C<undef> (the parameter represents a void return or absent output).
  249: When C<void> is used the schema must contain exactly one parameter.
  250: The C<min>/C<max> constraints apply to the B<length> (in characters) of the referenced string.
  251: All other string rules (C<matches>, C<nomatch>, C<memberof>, etc.) operate on the dereferenced string value.
  252: The validated return value is the dereferenced plain string.
  253: 
  254: A type can be an arrayref when a parameter could have different types (e.g. a string or an object).
  255: 
  256:   $schema = {
  257:     username => [
  258:       { type => 'string', min => 3, max => 50 },	# Name
  259:       { type => 'integer', 'min' => 1 },	# UID that isn't root
  260:     ]
  261:   };
  262: 
  263: As a shorthand, C<type> itself may be an arrayref of type name strings (a I<union type>)
  264: when all other constraints are shared between the alternatives:
  265: 
  266:   $schema = {
  267:     data => { type => ['string', 'arrayref'] },
  268:     id   => { type => ['string', 'integer'], optional => 1 },
  269:   };
  270: 
  271: This is equivalent to the full array-of-rules form but more concise.
  272: Every other key in the rule hash (C<optional>, C<min>, C<max>, C<matches>, etc.)
  273: is inherited by each candidate type and validated independently against it.
  274: Type names are tried left-to-right; the first match wins and its coercion
  275: (e.g. numeric types) is propagated back to the caller.
  276: If the value fails all candidate types, validation croaks with a message
  277: listing the union members.
  278: 
  279: =item * C<can>
  280: 
  281: The parameter must be an object that understands the method C<can>.
  282: C<can> can be a simple scalar string of a method name,
  283: or an arrayref of a list of method names, all of which must be supported by the object.
  284: 
  285:    $schema = {
  286:      gedcom => { type => object, can => 'get_individual' }
  287:    }
  288: 
  289: =item * C<isa>
  290: 
  291: The parameter must be an object of type C<isa>.
  292: 
  293: =item * C<memberof>
  294: 
  295: The parameter must be a member of the given arrayref.
  296: 
  297:   status => {
  298:     type => 'string',
  299:     memberof => ['draft', 'published', 'archived']
  300:   }
  301: 
  302:   priority => {
  303:     type => 'integer',
  304:     memberof => [1, 2, 3, 4, 5]
  305:   }
  306: 
  307: For string types, the comparison is case-sensitive by default. Use the C<case_sensitive>
  308: flag to control this behavior:
  309: 
  310:   # Case-sensitive (default) - must be exact match
  311:   code => {
  312:     type => 'string',
  313:     memberof => ['ABC', 'DEF', 'GHI']
  314:     # 'abc' will fail
  315:   }
  316: 
  317:   # Case-insensitive - any case accepted
  318:   code => {
  319:     type => 'string',
  320:     memberof => ['ABC', 'DEF', 'GHI'],
  321:     case_sensitive => 0
  322:     # 'abc', 'Abc', 'ABC' all pass, original case preserved
  323:   }
  324: 
  325: For numeric types (C<integer>, C<number>, C<float>), the comparison uses numeric
  326: equality (C<==> operator):
  327: 
  328:   rating => {
  329:     type => 'number',
  330:     memberof => [0.5, 1.0, 1.5, 2.0]
  331:   }
  332: 
  333: Note that C<memberof> cannot be combined with C<min> or C<max> constraints as they
  334: serve conflicting purposes - C<memberof> defines an explicit whitelist while C<min>/C<max>
  335: define ranges.
  336: 
  337: =item * C<enum>
  338: 
  339: Same as C<memberof>.
  340: 
  341: =item * C<values>
  342: 
  343: Same as C<memberof>.
  344: 
  345: =item * C<notmemberof>
  346: 
  347: The parameter must not be a member of the given arrayref (blacklist).
  348: This is the inverse of C<memberof>.
  349: 
  350:   username => {
  351:     type => 'string',
  352:     notmemberof => ['admin', 'root', 'system', 'administrator']
  353:   }
  354: 
  355:   port => {
  356:     type => 'integer',
  357:     notmemberof => [22, 23, 25, 80, 443]  # Reserved ports
  358:   }
  359: 
  360: Like C<memberof>, string comparisons are case-sensitive by default but can be controlled
  361: with the C<case_sensitive> flag:
  362: 
  363:   # Case-sensitive (default)
  364:   username => {
  365:     type => 'string',
  366:     notmemberof => ['Admin', 'Root']
  367:     # 'admin' would pass, 'Admin' would fail
  368:   }
  369: 
  370:   # Case-insensitive
  371:   username => {
  372:     type => 'string',
  373:     notmemberof => ['Admin', 'Root'],
  374:     case_sensitive => 0
  375:     # 'admin', 'ADMIN', 'Admin' all fail
  376:   }
  377: 
  378: The blacklist is checked after any C<transform> rules are applied, allowing you to
  379: normalize input before checking:
  380: 
  381:   username => {
  382:     type => 'string',
  383:     transform => sub { lc($_[0]) },  # Normalize to lowercase
  384:     notmemberof => ['admin', 'root', 'system']
  385:   }
  386: 
  387: C<notmemberof> can be combined with other validation rules:
  388: 
  389:   username => {
  390:     type => 'string',
  391:     notmemberof => ['admin', 'root', 'system'],
  392:     min => 3,
  393:     max => 20,
  394:     matches => qr/^[a-z0-9_]+$/
  395:   }
  396: 
  397: =item * C<case_sensitive>
  398: 
  399: A boolean value indicating whether string comparisons should be case-sensitive.
  400: This flag affects the C<memberof> and C<notmemberof> validation rules.
  401: The default value is C<1> (case-sensitive).
  402: 
  403: When set to C<0>, string comparisons are performed case-insensitively, allowing values
  404: with different casing to match. The original case of the input value is preserved in
  405: the validated output.
  406: 
  407:   # Case-sensitive (default)
  408:   status => {
  409:     type => 'string',
  410:     memberof => ['Draft', 'Published', 'Archived'] # Input 'draft' will fail - must match exact case
  411:   }
  412: 
  413:   # Case-insensitive
  414:   status => {
  415:     type => 'string',
  416:     memberof => ['Draft', 'Published', 'Archived'],
  417:     case_sensitive => 0 # Input 'draft', 'DRAFT', or 'DrAfT' will all pass
  418:   }
  419: 
  420:   country_code => {
  421:     type => 'string',
  422:     memberof => ['US', 'UK', 'CA', 'FR'],
  423:     case_sensitive => 0  # Accept 'us', 'US', 'Us', etc.
  424:   }
  425: 
  426: This flag has no effect on numeric types (C<integer>, C<number>, C<float>) as numbers
  427: do not have case.
  428: 
  429: =item * C<min>/C<minimum>
  430: 
  431: The minimum length (for strings in characters not bytes), value (for numbers) or number of keys (for hashrefs).
  432: 
  433: =item * C<max>
  434: 
  435: The maximum length (for strings in characters not bytes), value (for numbers) or number of keys (for hashrefs).
  436: 
  437: =item * C<matches>
  438: 
  439: A regular expression that the parameter value must match.
  440: Checks all members of arrayrefs.
  441: 
  442: =item * C<nomatch>
  443: 
  444: A regular expression that the parameter value must not match.
  445: Checks all members of arrayrefs.
  446: 
  447: =item * C<position>
  448: 
  449: For routines and methods that take positional args,
  450: this integer value defines which position the argument will be in.
  451: If this is set for all arguments,
  452: C<validate_strict> will return a reference to an array, rather than a reference to a hash.
  453: 
  454: =item * C<regex>
  455: 
  456: Synonym of matches
  457: 
  458: =item * C<description>
  459: 
  460: The description of the rule
  461: 
  462: =item * C<callback>
  463: 
  464: A code reference to a subroutine that performs custom validation logic.
  465: The subroutine should accept the parameter value, the argument list and the schema as arguments and return true if the value is valid, false otherwise.
  466: 
  467: Use this to test more complex examples:
  468: 
  469:   my $schema = {
  470:     even_number => {
  471:       type => 'integer',
  472:       callback => sub { $_[0] % 2 == 0 }
  473:   };
  474: 
  475:   # Specify the arguments for a routine which has a second, optional argument, which, if given, must be less than or equal to the first
  476:   my $schema = {
  477:     first => {
  478:       type => 'integer'
  479:     }, second => {
  480:       type => 'integer',
  481:       optional => 1,
  482:       callback => sub {
  483:         my($value, $args) = @_;
  484: 	# The 'defined' is needed in case 'second' is evaluated before 'first'
  485: 	return (defined($args->{first}) && $value <= $args->{first}) ? 1 : 0
  486:       }
  487:     }
  488:   };
  489: 
  490: =item * C<optional>
  491: 
  492: A boolean value indicating whether the parameter is optional.
  493: If true, the parameter is not required.
  494: If false or omitted, the parameter is required.
  495: 
  496: It can be a reference to a code snippet that will return true or false,
  497: to determine if the parameter is optional or not.
  498: The code will be called with two arguments: the value of the parameter and hash ref of all parameters:
  499: 
  500:   my $schema = {
  501:     optional_field => {
  502:       type => 'string',
  503:       optional => sub {
  504:         my ($value, $all_params) = @_;
  505:         return $all_params->{make_optional} ? 1 : 0;
  506:       }
  507:     },
  508:     make_optional => { type => 'boolean' }
  509:   };
  510: 
  511:   my $result = validate_strict(schema => $schema, input => { make_optional => 1 });
  512: 
  513: If the parameter is not optional, it can be passed an undef value, which will not flag an error.
  514: This is by design.
  515: So this will not say that the required parameter 's' is missing:
  516: 
  517:     validate_strict(
  518:         schema => { s => { type => 'string' } },
  519:         input  => { s => undef },
  520:     );
  521: 
  522: =item * C<default>
  523: 
  524: Populate missing optional parameters with the specified value.
  525: Note that this value is not validated.
  526: 
  527:   username => {
  528:     type => 'string',
  529:     optional => 1,
  530:     default => 'guest'
  531:   }
  532: 
  533: =item * C<element_type>
  534: 
  535: Extends the validation to individual elements of arrays.
  536: 
  537:   tags => {
  538:     type => 'arrayref',
  539:     element_type => 'number',	# Float means the same
  540:     min => 1,	# this is the length of the array, not the min value for each of the numbers. For that, add a C<schema> rule
  541:     max => 5
  542:   }
  543: 
  544: =item * C<error_msg>
  545: 
  546: The custom error message to be used in the event of a validation failure.
  547: 
  548:   age => {
  549:     type => 'integer',
  550:     min => 18,
  551:     error_msg => 'You must be at least 18 years old'
  552:   }
  553: 
  554: =item * C<nullable>
  555: 
  556: Like optional,
  557: though this cannot be a coderef,
  558: only a flag.
  559: 
  560: =item * C<schema>
  561: 
  562: You can validate nested hashrefs and arrayrefs using the C<schema> property:
  563: 
  564:     my $schema = {
  565:         user => {	# 'user' is a hashref
  566:             type => 'hashref',
  567:             schema => {	# Specify what the elements of the hash should be
  568:                 name => { type => 'string' },
  569:                 age => { type => 'integer', min => 0 },
  570:                 hobbies => {	# 'hobbies' is an array ref that this user has
  571:                     type => 'arrayref',
  572:                     schema => { type => 'string' }, # Validate each hobby
  573:                     min => 1 # At least one hobby
  574:                 }
  575:             }
  576:         }, metadata => {
  577:             type => 'hashref',
  578:             schema => {
  579:                 created => { type => 'string' },
  580:                 tags => {
  581:                     type => 'arrayref',
  582:                     schema => {
  583:                         type => 'string',
  584:                         matches => qr/^[a-z]+$/	# Or you can say matches => '^[a-z]+$'
  585:                     }
  586:                 }
  587:             }
  588:         }
  589:     };
  590: 
  591: =item * C<validate>
  592: 
  593: A snippet of code that validates the input.
  594: It's passed the input arguments,
  595: and return a string containing a reason for rejection,
  596: or undef if it's allowed.
  597: 
  598:     my $schema = {
  599:       user => {
  600:         type => 'string',
  601: 	validate => sub {
  602: 	  if($_[0]->{'password'} eq 'bar') {
  603: 	    return undef;
  604: 	  }
  605: 	  return 'Invalid password, try again';
  606: 	}
  607:       }, password => {
  608:          type => 'string'
  609:       }
  610:     };
  611: 
  612: =item * C<transform>
  613: 
  614: A code reference to a subroutine that transforms/sanitizes the parameter value before validation.
  615: The subroutine should accept the parameter value as an argument and return the transformed value.
  616: The transformation is applied before any validation rules are checked, allowing you to normalize
  617: or clean data before it is validated.
  618: 
  619: Common use cases include trimming whitespace, normalizing case, formatting phone numbers,
  620: sanitizing user input, and converting between data formats.
  621: 
  622:   # Simple string transformations
  623:   username => {
  624:     type => 'string',
  625:     transform => sub { lc(trim($_[0])) },  # lowercase and trim
  626:     matches => qr/^[a-z0-9_]+$/
  627:   }
  628: 
  629:   email => {
  630:     type => 'string',
  631:     transform => sub { lc(trim($_[0])) },  # normalize email
  632:     matches => qr/^[^@\s]+\@[^@\s]+\.[^@\s]+$/
  633:   }
  634: 
  635:   # Array transformations
  636:   tags => {
  637:     type => 'arrayref',
  638:     transform => sub { [map { lc($_) } @{$_[0]}] },  # lowercase all elements
  639:     element_type => 'string'
  640:   }

  642:   keywords => {
  643:     type => 'arrayref',
  644:     transform => sub {
  645:       my @arr = map { lc(trim($_)) } @{$_[0]};

  647:       return [grep { !$seen{$_}++ } @arr];  # remove duplicates
  648:     }
  649:   }

  651:   # Numeric transformations
  652:   quantity => {
  653:     type => 'integer',
  654:     transform => sub { int($_[0] + 0.5) },  # round to nearest integer
  655:     min => 1

  659:   slug => {
  660:     type => 'string',
  661:     transform => sub {

  664:       $str =~ s/\s+/-/g;      # replace spaces with hyphens

  672:     transform => sub {

  680: The C<transform> function is applied to the value before any validation checks (C<min>/C<minimum>, C<max>,
  681: C<matches>, C<callback>, etc.), ensuring that validation rules are checked against the cleaned data.
  682: 
  683: Transformations work with all parameter types including nested structures:
  684: 
  685:   user => {
  686:     type => 'hashref',

  693:         transform => sub { lc(trim($_[0])) }

  699: 
  700:   my $custom_types = {
  701:     email => {
  702:       type => 'string',
  703:       transform => sub { lc(trim($_[0])) },

  706:   };

  708: Note that the transformed value is what gets returned in the validated result and is what
  709: subsequent validation rules will check against. If a transformation might fail, ensure it
  710: handles edge cases appropriately.
  711: It is the responsibility of the transformer to ensure that the type of the returned value is correct,
  712: since that is what will be validated.
  713: 
  714: Many validators also allow a code ref to be passed so that you can create your own, conditional validation rule, e.g.:
  715: 
  716:   $schema = {
  717:     age => {
  718:       type => 'integer',
  719:       min => sub {

  722:       }
  723:     }
  724:   }

  726: =item * C<validator>
  727: 
  728: A synonym of C<validate>, for compatibility with L<Data::Processor>.
  729: 
  730: =item * C<cross_validation>
  731: 
  732: A reference to a hash that defines validation rules that depend on more than one parameter.
  733: Cross-field validations are performed after all individual parameter validations have passed,
  734: allowing you to enforce business logic that requires checking relationships between different fields.
  735: 
  736: Each cross-validation rule is a key-value pair where the key is a descriptive name for the validation
  737: and the value is a code reference that accepts a hash reference of all validated parameters.
  738: The subroutine should return C<undef> if the validation passes, or an error message string if it fails.
  739: 
  740:   my $schema = {
  741:     password => { type => 'string', min => 8 },
  742:     password_confirm => { type => 'string' }
  743:   };
  744: 
  745:   my $cross_validation = {
  746:     passwords_match => sub {
  747:       my $params = shift;
  748:       return $params->{password} eq $params->{password_confirm}
  749:         ? undef : "Passwords don't match";
  750:     }
  751:   };
  752: 
  753:   my $validated = validate_strict(
  754:     schema => $schema,
  755:     input => $input,
  756:     cross_validation => $cross_validation
  757:   );
  758: 
  759: Common use cases include password confirmation, date range validation, numeric comparisons,
  760: and conditional requirements:
  761: 
  762:   # Date range validation
  763:   my $cross_validation = {
  764:     date_range_valid => sub {
  765:       my $params = shift;
  766:       return $params->{start_date} le $params->{end_date}
  767:         ? undef : "Start date must be before or equal to end date";
  768:     }
  769:   };
  770: 
  771:   # Price range validation
  772:   my $cross_validation = {
  773:     price_range_valid => sub {
  774:       my $params = shift;
  775:       return $params->{min_price} <= $params->{max_price}
  776:         ? undef : "Minimum price must be less than or equal to maximum price";
  777:     }
  778:   };
  779: 
  780:   # Conditional required field
  781:   my $cross_validation = {
  782:     address_required_for_delivery => sub {
  783:       my $params = shift;
  784:       if ($params->{shipping_method} eq 'delivery' && !$params->{delivery_address}) {
  785:         return "Delivery address is required when shipping method is 'delivery'";
  786:       }
  787:       return undef;
  788:     }
  789:   };
  790: 
  791: Multiple cross-validations can be defined in the same hash, and they are all checked in order.
  792: If any cross-validation fails, the function will C<croak> with the error message returned by the validation:
  793: 
  794:   my $cross_validation = {
  795:     passwords_match => sub {
  796:       my $params = shift;
  797:       return $params->{password} eq $params->{password_confirm}
  798:         ? undef : "Passwords don't match";
  799:     },
  800:     emails_match => sub {
  801:       my $params = shift;
  802:       return $params->{email} eq $params->{email_confirm}
  803:         ? undef : "Email addresses don't match";
  804:     },
  805:     age_matches_birth_year => sub {
  806:       my $params = shift;
  807:       my $current_year = (localtime)[5] + 1900;
  808:       my $calculated_age = $current_year - $params->{birth_year};
  809:       return abs($calculated_age - $params->{age}) <= 1
  810:         ? undef : "Age doesn't match birth year";
  811:     }
  812:   };

  814: Cross-validations receive the parameters after individual validation and transformation have been applied,
  815: so you can rely on the data being in the correct format and type:
  816: 
  817:   my $schema = {
  818:     email => {
  819:       type => 'string',
  820:       transform => sub { lc($_[0]) }  # Lowercased before cross-validation

  824:       transform => sub { lc($_[0]) }

  837: Cross-validations can access nested structures and optional fields:
  838: 
  839:   my $cross_validation = {
  840:     guardian_required_for_minors => sub {

  873: =item * C<relationships>
  874: 
  875: A reference to an array that defines validation rules based on relationships between parameters.
  876: Relationship validations are performed after all individual parameter validations have passed,
  877: but before cross-validations.
  878: 
  879: Each relationship is a hash reference with a C<type> field and additional fields depending on the type:
  880: 
  881: =over 4
  882: 
  883: =item * B<mutually_exclusive>
  884: 
  885: Parameters that cannot be specified together.
  886: 
  887:   relationships => [
  888:     {
  889:       type => 'mutually_exclusive',
  890:       params => ['file', 'content'],
  891:       description => 'Cannot specify both file and content'
  892:     }
  893:   ]
  894: 
  895: =item * B<required_group>
  896: 
  897: At least one parameter from the group must be specified.
  898: 
  899:   relationships => [
  900:     {
  901:       type => 'required_group',
  902:       params => ['id', 'name'],
  903:       logic => 'or',
  904:       description => 'Must specify either id or name'
  905:     }
  906:   ]
  907: 
  908: =item * B<conditional_requirement>
  909: 
  910: If one parameter is specified, another becomes required.
  911: 
  912:   relationships => [
  913:     {
  914:       type => 'conditional_requirement',
  915:       if => 'async',
  916:       then_required => 'callback',
  917:       description => 'When async is specified, callback is required'
  918:     }
  919:   ]
  920: 
  921: =item * B<dependency>
  922: 
  923: One parameter requires another to be present.
  924: 
  925:   relationships => [
  926:     {
  927:       type => 'dependency',
  928:       param => 'port',
  929:       requires => 'host',
  930:       description => 'port requires host to be specified'
  931:     }
  932:   ]
  933: 
  934: =item * B<value_constraint>
  935: 
  936: Specific value requirements between parameters.
  937: 
  938:   relationships => [
  939:     {
  940:       type => 'value_constraint',
  941:       if => 'ssl',
  942:       then => 'port',
  943:       operator => '==',
  944:       value => 443,
  945:       description => 'When ssl is specified, port must equal 443'
  946:     }
  947:   ]
  948: 
  949: =item * B<value_conditional>
  950: 
  951: Parameter required when another has a specific value.
  952: 
  953:   relationships => [
  954:     {
  955:       type => 'value_conditional',
  956:       if => 'mode',
  957:       equals => 'secure',
  958:       then_required => 'key',
  959:       description => "When mode equals 'secure', key is required"
  960:     }
  961:   ]
  962: 
  963: =back
  964: 
  965: If a parameter is optional and its value is C<undef>,
  966: validation will be skipped for that parameter.
  967: 
  968: If the validation fails, the function will C<croak> with an error message describing the validation failure.
  969: 
  970: If the validation is successful, the function will return a reference to a new hash containing the validated and (where applicable) coerced parameters.  Integer and number parameters will be coerced to their respective types.
  971: 
  972: The C<description> field is optional but recommended for clearer error messages.
  973: 
  974: =back
