   85: =head2 validate_strict
   86: 
   87: Validates a set of parameters against a schema.
   88: 
   89: This function takes two mandatory arguments:
   90: 
   91: =over 4
   92: 
   93: =item * C<schema> || C<members>
   94: 
   95: A reference to a hash that defines the validation rules for each parameter.
   96: The keys of the hash are the parameter names, and the values are either a string representing the parameter type or a reference to a hash containing more detailed rules.
   97: 
   98: As an alternative the schema may be supplied as an B<arrayref of parameter hashrefs>,
   99: where every element describes one parameter and carries a mandatory
  100: C<name> key:
  101: 
  102:   $schema = [
  103:     { name => 'username', type => 'string', min => 3, max => 50 },
  104:     { name => 'age',      type => 'integer', min => 0, max => 150 },
  105:     { name => 'role',     type => 'string', optional => 1, default => 'user' },
  106:   ];
  107: 
  108: The arrayref form is normalised to the standard hashref form before any further
  109: processing.  It is particularly useful when declaration order matters (e.g.
  110: for positional or mixed calling conventions used by some CPAN modules).  The
  111: C<name> key is consumed during normalisation and does not appear as a
  112: validation rule.
  113: 
  114: For some sort of compatibility with L<Data::Processor>,
  115: it is possible to wrap the schema within a hash like this:
  116: 
  117:   $schema = {
  118:     description => 'Describe what this schema does',
  119:     error_msg => 'An error message',
  120:     schema => {
  121:       # ... schema goes here
  122:     }
  123:   }
  124: 
  125: =item * C<args> || C<input>
  126: 
  127: A reference to a hash containing the parameters to be validated.
  128: The keys of the hash are the parameter names, and the values are the parameter values.
  129: 
  130: =back
  131: 
  132: It takes optional arguments:
  133: 
  134: =over 4
  135: 
  136: =item * C<description>
  137: 
  138: What the schema does,
  139: used in error messages.
  140: 
  141: =item * C<error_msg>
  142: 
  143: Overrides the default message when something doesn't validate.
  144: 
  145: =item * C<unknown_parameter_handler>
  146: 
  147: This parameter describes what to do when a parameter is given that is not in the schema of valid parameters.
  148: It must be one of C<die>, C<warn>, or C<ignore>.
  149: 
  150: It defaults to C<die> unless C<carp_on_warn> is given, in which case it defaults to C<warn>.
  151: 
  152: =item * C<logger>
  153: 
  154: A logging object that understands messages such as C<error> and C<warn>.
  155: 
  156: =item * C<custom_types>
  157: 
  158: A reference to a hash that defines reusable custom types.
  159: Custom types allow you to define validation rules once and reuse them throughout your schema,
  160: making your validation logic more maintainable and readable.
  161: 
  162: Each custom type is defined as a hash reference containing the same validation rules available for regular parameters
  163: (C<type>, C<min>, C<max>, C<matches>, C<memberof>, C<values>, C<enum>, C<notmemberof>, C<callback>, etc.).
  164: 
  165:   my $custom_types = {
  166:     email => {
  167:       type => 'string',
  168:       matches => qr/^[^@\s]+\@[^@\s]+\.[^@\s]+$/,
  169:       error_msg => 'Invalid email address format'
  170:     }, phone => {
  171:       type => 'string',
  172:       matches => qr/^\+?[1-9]\d{1,14}$/,
  173:       min => 10,
  174:       max => 15
  175:     }, percentage => {
  176:       type => 'number',
  177:       min => 0,
  178:       max => 100
  179:     }, status => {
  180:       type => 'string',
  181:       memberof => ['draft', 'published', 'archived']
  182:     }
  183:   };
  184: 
  185:   my $schema = {
  186:     user_email => { type => 'email' },
  187:     contact_number => { type => 'phone', optional => 1 },
  188:     completion => { type => 'percentage' },
  189:     post_status => { type => 'status' }
  190:   };
  191: 
  192:   my $validated = validate_strict(
  193:     schema => $schema,
  194:     input => $input,
  195:     custom_types => $custom_types
  196:   );
  197: 
  198: Custom types can be extended or overridden in the schema by specifying additional constraints:
  199: 
  200:   my $schema = {
  201:     admin_username => {
  202:       type => 'username',  # Uses custom type definition
  203:       min => 5,            # Overrides custom type's min value
  204:       max => 15            # Overrides custom type's max value
  205:     }
  206:   };
  207: 
  208: Custom types work seamlessly with nested schema, optional parameters, and all other validation features.
  209: 
  210: =back
  211: 
  212: The schema can define the following rules for each parameter:
  213: 
  214: =over 4
  215: 
  216: =item * C<type>
  217: 
  218: The data type of the parameter.
  219: Valid types are C<string>, C<integer>, C<number>, C<float> C<boolean>, C<scalar>, C<scalarref>, C<stringref>, C<hashref>, C<arrayref>, C<object>, C<coderef> and C<void>.
  220: C<scalar> accepts any plain scalar value (string, number, boolean, etc.) but rejects references (arrayrefs, hashrefs, coderefs, objects).
  221: C<scalarref> accepts a reference to a scalar value (e.g. C<\$var>) but rejects plain scalars, arrayrefs, hashrefs, coderefs, and objects.
  222: C<stringref> accepts a reference to a scalar that contains a plain string (e.g. C<\$str>) and rejects plain scalars, references-to-references, arrayrefs, hashrefs, coderefs, and objects.
  223: C<void> asserts that the parameter value is C<undef> (the parameter represents a void return or absent output).
  224: When C<void> is used the schema must contain exactly one parameter.
  225: The C<min>/C<max> constraints apply to the B<length> (in characters) of the referenced string.
  226: All other string rules (C<matches>, C<nomatch>, C<memberof>, etc.) operate on the dereferenced string value.
  227: The validated return value is the dereferenced plain string.
  228: 
  229: A type can be an arrayref when a parameter could have different types (e.g. a string or an object).
  230: 
  231:   $schema = {
  232:     username => [
  233:       { type => 'string', min => 3, max => 50 },	# Name
  234:       { type => 'integer', 'min' => 1 },	# UID that isn't root
  235:     ]
  236:   };
  237: 
  238: As a shorthand, C<type> itself may be an arrayref of type name strings (a I<union type>)
  239: when all other constraints are shared between the alternatives:
  240: 
  241:   $schema = {
  242:     data => { type => ['string', 'arrayref'] },
  243:     id   => { type => ['string', 'integer'], optional => 1 },
  244:   };
  245: 
  246: This is equivalent to the full array-of-rules form but more concise.
  247: Every other key in the rule hash (C<optional>, C<min>, C<max>, C<matches>, etc.)
  248: is inherited by each candidate type and validated independently against it.
  249: Type names are tried left-to-right; the first match wins and its coercion
  250: (e.g. numeric types) is propagated back to the caller.
  251: If the value fails all candidate types, validation croaks with a message
  252: listing the union members.
  253: 
  254: =item * C<can>
  255: 
  256: The parameter must be an object that understands the method C<can>.
  257: C<can> can be a simple scalar string of a method name,
  258: or an arrayref of a list of method names, all of which must be supported by the object.
  259: 
  260:    $schema = {
  261:      gedcom => { type => object, can => 'get_individual' }
  262:    }
  263: 
  264: =item * C<isa>
  265: 
  266: The parameter must be an object of type C<isa>.
  267: 
  268: =item * C<memberof>
  269: 
  270: The parameter must be a member of the given arrayref.
  271: 
  272:   status => {
  273:     type => 'string',
  274:     memberof => ['draft', 'published', 'archived']
  275:   }
  276: 
  277:   priority => {
  278:     type => 'integer',
  279:     memberof => [1, 2, 3, 4, 5]
  280:   }
  281: 
  282: For string types, the comparison is case-sensitive by default. Use the C<case_sensitive>
  283: flag to control this behavior:
  284: 
  285:   # Case-sensitive (default) - must be exact match
  286:   code => {
  287:     type => 'string',
  288:     memberof => ['ABC', 'DEF', 'GHI']
  289:     # 'abc' will fail
  290:   }
  291: 
  292:   # Case-insensitive - any case accepted
  293:   code => {
  294:     type => 'string',
  295:     memberof => ['ABC', 'DEF', 'GHI'],
  296:     case_sensitive => 0
  297:     # 'abc', 'Abc', 'ABC' all pass, original case preserved
  298:   }
  299: 
  300: For numeric types (C<integer>, C<number>, C<float>), the comparison uses numeric
  301: equality (C<==> operator):
  302: 
  303:   rating => {
  304:     type => 'number',
  305:     memberof => [0.5, 1.0, 1.5, 2.0]
  306:   }
  307: 
  308: Note that C<memberof> cannot be combined with C<min> or C<max> constraints as they
  309: serve conflicting purposes - C<memberof> defines an explicit whitelist while C<min>/C<max>
  310: define ranges.
  311: 
  312: =item * C<enum>
  313: 
  314: Same as C<memberof>.
  315: 
  316: =item * C<values>
  317: 
  318: Same as C<memberof>.
  319: 
  320: =item * C<notmemberof>
  321: 
  322: The parameter must not be a member of the given arrayref (blacklist).
  323: This is the inverse of C<memberof>.
  324: 
  325:   username => {
  326:     type => 'string',
  327:     notmemberof => ['admin', 'root', 'system', 'administrator']
  328:   }
  329: 
  330:   port => {
  331:     type => 'integer',
  332:     notmemberof => [22, 23, 25, 80, 443]  # Reserved ports
  333:   }
  334: 
  335: Like C<memberof>, string comparisons are case-sensitive by default but can be controlled
  336: with the C<case_sensitive> flag:
  337: 
  338:   # Case-sensitive (default)
  339:   username => {
  340:     type => 'string',
  341:     notmemberof => ['Admin', 'Root']
  342:     # 'admin' would pass, 'Admin' would fail
  343:   }
  344: 
  345:   # Case-insensitive
  346:   username => {
  347:     type => 'string',
  348:     notmemberof => ['Admin', 'Root'],
  349:     case_sensitive => 0
  350:     # 'admin', 'ADMIN', 'Admin' all fail
  351:   }
  352: 
  353: The blacklist is checked after any C<transform> rules are applied, allowing you to
  354: normalize input before checking:
  355: 
  356:   username => {
  357:     type => 'string',
  358:     transform => sub { lc($_[0]) },  # Normalize to lowercase
  359:     notmemberof => ['admin', 'root', 'system']
  360:   }
  361: 
  362: C<notmemberof> can be combined with other validation rules:
  363: 
  364:   username => {
  365:     type => 'string',
  366:     notmemberof => ['admin', 'root', 'system'],
  367:     min => 3,
  368:     max => 20,
  369:     matches => qr/^[a-z0-9_]+$/
  370:   }
  371: 
  372: =item * C<case_sensitive>
  373: 
  374: A boolean value indicating whether string comparisons should be case-sensitive.
  375: This flag affects the C<memberof> and C<notmemberof> validation rules.
  376: The default value is C<1> (case-sensitive).
  377: 
  378: When set to C<0>, string comparisons are performed case-insensitively, allowing values
  379: with different casing to match. The original case of the input value is preserved in
  380: the validated output.
  381: 
  382:   # Case-sensitive (default)
  383:   status => {
  384:     type => 'string',
  385:     memberof => ['Draft', 'Published', 'Archived'] # Input 'draft' will fail - must match exact case
  386:   }
  387: 
  388:   # Case-insensitive
  389:   status => {
  390:     type => 'string',
  391:     memberof => ['Draft', 'Published', 'Archived'],
  392:     case_sensitive => 0 # Input 'draft', 'DRAFT', or 'DrAfT' will all pass
  393:   }
  394: 
  395:   country_code => {
  396:     type => 'string',
  397:     memberof => ['US', 'UK', 'CA', 'FR'],
  398:     case_sensitive => 0  # Accept 'us', 'US', 'Us', etc.
  399:   }
  400: 
  401: This flag has no effect on numeric types (C<integer>, C<number>, C<float>) as numbers
  402: do not have case.
  403: 
  404: =item * C<min>/C<minimum>
  405: 
  406: The minimum length (for strings in characters not bytes), value (for numbers) or number of keys (for hashrefs).
  407: 
  408: =item * C<max>
  409: 
  410: The maximum length (for strings in characters not bytes), value (for numbers) or number of keys (for hashrefs).
  411: 
  412: =item * C<matches>
  413: 
  414: A regular expression that the parameter value must match.
  415: Checks all members of arrayrefs.
  416: 
  417: =item * C<nomatch>
  418: 
  419: A regular expression that the parameter value must not match.
  420: Checks all members of arrayrefs.
  421: 
  422: =item * C<position>
  423: 
  424: For routines and methods that take positional args,
  425: this integer value defines which position the argument will be in.
  426: If this is set for all arguments,
  427: C<validate_strict> will return a reference to an array, rather than a reference to a hash.
  428: 
  429: =item * C<regex>
  430: 
  431: Synonym of matches
  432: 
  433: =item * C<description>
  434: 
  435: The description of the rule
  436: 
  437: =item * C<callback>
  438: 
  439: A code reference to a subroutine that performs custom validation logic.
  440: The subroutine should accept the parameter value, the argument list and the schema as arguments and return true if the value is valid, false otherwise.
  441: 
  442: Use this to test more complex examples:
  443: 
  444:   my $schema = {
  445:     even_number => {
  446:       type => 'integer',
  447:       callback => sub { $_[0] % 2 == 0 }
  448:   };
  449: 
  450:   # Specify the arguments for a routine which has a second, optional argument, which, if given, must be less than or equal to the first
  451:   my $schema = {
  452:     first => {
  453:       type => 'integer'
  454:     }, second => {
  455:       type => 'integer',
  456:       optional => 1,
  457:       callback => sub {
  458:         my($value, $args) = @_;
  459: 	# The 'defined' is needed in case 'second' is evaluated before 'first'
  460: 	return (defined($args->{first}) && $value <= $args->{first}) ? 1 : 0
  461:       }
  462:     }
  463:   };
  464: 
  465: =item * C<optional>
  466: 
  467: A boolean value indicating whether the parameter is optional.
  468: If true, the parameter is not required.
  469: If false or omitted, the parameter is required.
  470: 
  471: It can be a reference to a code snippet that will return true or false,
  472: to determine if the parameter is optional or not.
  473: The code will be called with two arguments: the value of the parameter and hash ref of all parameters:
  474: 
  475:   my $schema = {
  476:     optional_field => {
  477:       type => 'string',
  478:       optional => sub {
  479:         my ($value, $all_params) = @_;
  480:         return $all_params->{make_optional} ? 1 : 0;
  481:       }
  482:     },
  483:     make_optional => { type => 'boolean' }
  484:   };
  485: 
  486:   my $result = validate_strict(schema => $schema, input => { make_optional => 1 });
  487: 
  488: If the parameter is not optional, it can be passed an undef value, which will not flag an error.
  489: This is by design.
  490: So this will not say that the required parameter 's' is missing:
  491: 
  492:     validate_strict(
  493:         schema => { s => { type => 'string' } },
  494:         input  => { s => undef },
  495:     );
  496: 
  497: =item * C<default>
  498: 
  499: Populate missing optional parameters with the specified value.
  500: Note that this value is not validated.
  501: 
  502:   username => {
  503:     type => 'string',
  504:     optional => 1,
  505:     default => 'guest'
  506:   }
  507: 
  508: =item * C<element_type>
  509: 
  510: Extends the validation to individual elements of arrays.
  511: 
  512:   tags => {
  513:     type => 'arrayref',
  514:     element_type => 'number',	# Float means the same
  515:     min => 1,	# this is the length of the array, not the min value for each of the numbers. For that, add a C<schema> rule
  516:     max => 5
  517:   }
  518: 
  519: =item * C<error_msg>
  520: 
  521: The custom error message to be used in the event of a validation failure.
  522: 
  523:   age => {
  524:     type => 'integer',
  525:     min => 18,
  526:     error_msg => 'You must be at least 18 years old'
  527:   }
  528: 
  529: =item * C<nullable>
  530: 
  531: Like optional,
  532: though this cannot be a coderef,
  533: only a flag.
  534: 
  535: =item * C<schema>
  536: 
  537: You can validate nested hashrefs and arrayrefs using the C<schema> property:
  538: 
  539:     my $schema = {
  540:         user => {	# 'user' is a hashref
  541:             type => 'hashref',
  542:             schema => {	# Specify what the elements of the hash should be
  543:                 name => { type => 'string' },
  544:                 age => { type => 'integer', min => 0 },
  545:                 hobbies => {	# 'hobbies' is an array ref that this user has
  546:                     type => 'arrayref',
  547:                     schema => { type => 'string' }, # Validate each hobby
  548:                     min => 1 # At least one hobby
  549:                 }
  550:             }
  551:         }, metadata => {
  552:             type => 'hashref',
  553:             schema => {
  554:                 created => { type => 'string' },
  555:                 tags => {
  556:                     type => 'arrayref',
  557:                     schema => {
  558:                         type => 'string',
  559:                         matches => qr/^[a-z]+$/	# Or you can say matches => '^[a-z]+$'
  560:                     }
  561:                 }
  562:             }
  563:         }
  564:     };
  565: 
  566: =item * C<validate>
  567: 
  568: A snippet of code that validates the input.
  569: It's passed the input arguments,
  570: and return a string containing a reason for rejection,
  571: or undef if it's allowed.
  572: 
  573:     my $schema = {
  574:       user => {
  575:         type => 'string',
  576: 	validate => sub {
  577: 	  if($_[0]->{'password'} eq 'bar') {
  578: 	    return undef;
  579: 	  }
  580: 	  return 'Invalid password, try again';
  581: 	}
  582:       }, password => {
  583:          type => 'string'
  584:       }
  585:     };

  587: =item * C<transform>
  588: 
  589: A code reference to a subroutine that transforms/sanitizes the parameter value before validation.
  590: The subroutine should accept the parameter value as an argument and return the transformed value.
  591: The transformation is applied before any validation rules are checked, allowing you to normalize
  592: or clean data before it is validated.
  593: 
  594: Common use cases include trimming whitespace, normalizing case, formatting phone numbers,
  595: sanitizing user input, and converting between data formats.
  596: 
  597:   # Simple string transformations
  598:   username => {
  599:     type => 'string',
  600:     transform => sub { lc(trim($_[0])) },  # lowercase and trim
  601:     matches => qr/^[a-z0-9_]+$/
  602:   }
  603: 
  604:   email => {
  605:     type => 'string',
  606:     transform => sub { lc(trim($_[0])) },  # normalize email
  607:     matches => qr/^[^@\s]+\@[^@\s]+\.[^@\s]+$/
  608:   }
  609: 
  610:   # Array transformations
  611:   tags => {
  612:     type => 'arrayref',
  613:     transform => sub { [map { lc($_) } @{$_[0]}] },  # lowercase all elements
  614:     element_type => 'string'
  615:   }
  616: 
  617:   keywords => {
  618:     type => 'arrayref',
  619:     transform => sub {
  620:       my @arr = map { lc(trim($_)) } @{$_[0]};
  621:       my %seen;
  622:       return [grep { !$seen{$_}++ } @arr];  # remove duplicates
  623:     }
  624:   }
  625: 
  626:   # Numeric transformations
  627:   quantity => {
  628:     type => 'integer',

  702: 
  703: A synonym of C<validate>, for compatibility with L<Data::Processor>.

  705: =item * C<cross_validation>
  706: 
  707: A reference to a hash that defines validation rules that depend on more than one parameter.
  708: Cross-field validations are performed after all individual parameter validations have passed,
  709: allowing you to enforce business logic that requires checking relationships between different fields.
  710: 
  711: Each cross-validation rule is a key-value pair where the key is a descriptive name for the validation
  712: and the value is a code reference that accepts a hash reference of all validated parameters.
  713: The subroutine should return C<undef> if the validation passes, or an error message string if it fails.
  714: 
  715:   my $schema = {
  716:     password => { type => 'string', min => 8 },
  717:     password_confirm => { type => 'string' }
  718:   };
  719: 
  720:   my $cross_validation = {
  721:     passwords_match => sub {
  722:       my $params = shift;
  723:       return $params->{password} eq $params->{password_confirm}
  724:         ? undef : "Passwords don't match";
  725:     }
  726:   };
  727: 
  728:   my $validated = validate_strict(
  729:     schema => $schema,
  730:     input => $input,
  731:     cross_validation => $cross_validation
  732:   );
  733: 
  734: Common use cases include password confirmation, date range validation, numeric comparisons,
  735: and conditional requirements:
  736: 
  737:   # Date range validation
  738:   my $cross_validation = {

  740:       my $params = shift;
  741:       return $params->{start_date} le $params->{end_date}
  742:         ? undef : "Start date must be before or equal to end date";
  743:     }
  744:   };

  746:   # Price range validation
  747:   my $cross_validation = {
  748:     price_range_valid => sub {
  749:       my $params = shift;

  751:         ? undef : "Minimum price must be less than or equal to maximum price";
  752:     }
  753:   };

  755:   # Conditional required field
  756:   my $cross_validation = {
  757:     address_required_for_delivery => sub {
  758:       my $params = shift;

  760:         return "Delivery address is required when shipping method is 'delivery'";

  766: Multiple cross-validations can be defined in the same hash, and they are all checked in order.
  767: If any cross-validation fails, the function will C<croak> with the error message returned by the validation:
  768: 
  769:   my $cross_validation = {

  787:   };

  848: =item * C<relationships>
  849: 
  850: A reference to an array that defines validation rules based on relationships between parameters.
  851: Relationship validations are performed after all individual parameter validations have passed,
  852: but before cross-validations.
  853: 
  854: Each relationship is a hash reference with a C<type> field and additional fields depending on the type:
  855: 
  856: =over 4
  857: 
  858: =item * B<mutually_exclusive>
  859: 
  860: Parameters that cannot be specified together.
  861: 
  862:   relationships => [
  863:     {
  864:       type => 'mutually_exclusive',
  865:       params => ['file', 'content'],
  866:       description => 'Cannot specify both file and content'
  867:     }
  868:   ]
  869: 
  870: =item * B<required_group>
  871: 
  872: At least one parameter from the group must be specified.
  873: 
  874:   relationships => [
  875:     {
  876:       type => 'required_group',
  877:       params => ['id', 'name'],
  878:       logic => 'or',
  879:       description => 'Must specify either id or name'
  880:     }
  881:   ]
  882: 
  883: =item * B<conditional_requirement>
  884: 
  885: If one parameter is specified, another becomes required.
  886: 
  887:   relationships => [
  888:     {
  889:       type => 'conditional_requirement',
  890:       if => 'async',
  891:       then_required => 'callback',
  892:       description => 'When async is specified, callback is required'
  893:     }
  894:   ]
  895: 
  896: =item * B<dependency>
  897: 
  898: One parameter requires another to be present.
  899: 
  900:   relationships => [
  901:     {
  902:       type => 'dependency',
  903:       param => 'port',
  904:       requires => 'host',
  905:       description => 'port requires host to be specified'
  906:     }
  907:   ]
  908: 
  909: =item * B<value_constraint>
  910: 
  911: Specific value requirements between parameters.
  912: 
  913:   relationships => [
  914:     {
  915:       type => 'value_constraint',
  916:       if => 'ssl',
  917:       then => 'port',
  918:       operator => '==',
  919:       value => 443,
  920:       description => 'When ssl is specified, port must equal 443'
  921:     }
  922:   ]
  923: 
  924: =item * B<value_conditional>
  925: 
  926: Parameter required when another has a specific value.
  927: 
  928:   relationships => [
  929:     {
  930:       type => 'value_conditional',
  931:       if => 'mode',
  932:       equals => 'secure',
  933:       then_required => 'key',
  934:       description => "When mode equals 'secure', key is required"
  935:     }
  936:   ]
  937: 
  938: =back
  939: 
  940: If a parameter is optional and its value is C<undef>,
  941: validation will be skipped for that parameter.
  942: 
  943: If the validation fails, the function will C<croak> with an error message describing the validation failure.
  944: 
  945: If the validation is successful, the function will return a reference to a new hash containing the validated and (where applicable) coerced parameters.  Integer and number parameters will be coerced to their respective types.
  946: 
  947: The C<description> field is optional but recommended for clearer error messages.
  948: 
  949: =back

 2328: Callers that require untainted values must perform their own regex capture after
 2329: validation, for example:
 2330: 
 2331:     my $validated = validate_strict(%args);
 2332:     my ($safe_name) = ($validated->{name} =~ /\A([\w\s]+)\z/);
 2333: 
 2334: =head2 User-supplied regex patterns
 2335: 
 2336: The C<matches> rule accepts pre-compiled C<qr//> objects supplied by the caller.
 2337: A pathologically constructed pattern (e.g. C<qr/(a+)+b/>) can cause catastrophic
 2338: backtracking and peg a CPU core when matched against a hostile input value.
 2339: Use possessive quantifiers (C<++>) or atomic groups (C<< (?>...) >>) in any
 2340: C<matches> pattern that will be applied to untrusted data.
 2341: 
 2342: =head2 Error message content
 2343: 
 2344: Error and warning messages produced by this module may include the parameter
 2345: value supplied by the caller.
 2346: The module strips ASCII control characters (including CR and LF) from all
 2347: messages before passing them to the logger or croaking, to prevent log-injection
 2348: and HTTP response-splitting attacks.
 2349: Callers should nevertheless apply their own output encoding before including any
 2350: validated value in an HTTP response, HTML page, or structured log entry.
